# RT-3378 — выпуск пакета без проверки, что собранное загружается

Задача RT-3378, запись от 2026-11-18.

## Просьба владельца

> пиши обвязку которая не позволит тебе выпускать сломанные пакеты

Тем же днём: «ты обязан создать обвязку которая не позволит тебе повторить этот провал».

## Что нашли

Версия `0.2.0` пакета протокола чата вышла в npm и не загружалась в Node. Пакет собрали копией процесса соседнего пакета без шага `verify`, а набор перед пушем берёт только проекты с такой целью, поэтому зелёный набор ничего не говорил о загрузке. Тот же пробел был у четырёх пакетов авторизации и системы управления содержимым: у них тоже не было цели `verify`. Здесь он закрыт для двух пакетов CMS; два пакета авторизации ушли в задачу RT-3379. Ещё один: в процессах `utils` и протокола чата коммит версии и тег ставились до сборки, и упавшая проверка оставила бы занятый номер без пакета. Отдельный пробел: процесс публикации писал заголовки коммитов с областью, которой не было в списке проверки коммитов, и первый выпуск упал на шаге версии.

## Решения

- Общая проверка собранного пакета `tools/verify-package.cjs` вместо копии под каждый пакет. Она загружает `esm` и `cjs`, ищет относительные импорты без расширения, необъявленные зависимости и ставит пакет из тарболла в пустую папку. Отвергнуто: проверка, написанная под один пакет.
- К запрету следов Angular в собранном пакете добавлена проверка «импорт объявлен в манифесте», а прямой запрет `rxjs` и `@angular` заменён ею: серверные пакеты законно зависят от Nest и `rxjs`, у пакета без объявленных зависимостей результат тот же.
- Пакет, зависящий от соседнего пакета рабочего пространства, загружается только из установленного тарболла: соседа не видно из `dist`.
- Проверка привязки `tools/check-package-release.mjs` читает все пакеты, собираемые двумя `tsc`: цель `verify`, корневая сборка с `nx verify`, процесс публикации, заголовки коммитов процесса. Она стоит в наборе перед пушем и в CI.
- Преграда выпуску — корневая команда `build:<пакет>` с `nx verify` на конце: её запускает сам процесс публикации, поэтому она держит при любом способе запуска. Хук `package-release-guard.sh` лишь быстрее отказывает по командной строке агента и экономит минуты запуска, который упал бы на этой преграде. Запуск из браузера, через `gh api` или по имени процесса хук не видит.
- Сборка с проверкой загрузки поставлена до шага версии в процессах `utils` и протокола чата, порядок держит проверка привязки.
- Правило `package-release` и шаблон `package-release-run`.

## Что не доделано

- Не проверен сторонний сборщик или среда потребителя: проверка загружает пакет в Node и из тарболла.
- Шаг тарболла берёт зависимости из реестра, версия соседнего пакета в манифесте должна уже быть опубликована.
- Сужение тяжёлых шагов набора перед пушем идёт отдельным предложением в пакет правил.
- Два пакета авторизации (`auth-contract`, `auth-server`) названы в проверке привязки исключением `NOT_JUDGED`: правка `projects/auth-*` считается правкой приёмника и требует e2e-теста для строки без поведения; цель `verify` для них в задаче RT-3379.
- `agent-kit` и `auth-import` не собираются двумя `tsc`, их корневые `build:*` без `nx verify`: проверка привязки их не судит. `agent-kit` с `bin` дороже всего ломать, это отдельная задача.
- Пакеты с Angular (`core`, `store`, `ui-kit-v2`, пакеты Angular авторизации и CMS) проверкой привязки не судятся: у них нет цели `verify`. Решение, нужна ли она им, остаётся за владельцем.
- Шаг тарболла идёт только в выпуске и вручную, в запусках на PR и на push он пропускается: без этого каждый PR платил бы за установку из реестра.
