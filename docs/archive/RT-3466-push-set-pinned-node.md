## Что сделано

- Функции в `facts.sh` читают `.nvmrc` — первую строку без комментария, без пробелов и метки
  порядка байтов — и дают каталог закреплённой node под nvm: точную версию, без неё старшую той же
  главной версии не ниже закреплённой; для главной версии или пары «главная.младшая» — старшую
  подходящую; установка без исполняемой node пропускается. Версии сравниваются по частям числами.
- Набор, набор вперёд и перемер перед PR ставят этот каталог первым в `PATH` для шагов и их выбора;
  набор возвращает `PATH`.
- Нет node, которая годится для закрепления, ни в nvm, ни в `PATH` — ни один шаг не идёт. Проверка
  отправки и git-хук отказывают одной строкой с обеими версиями и `nvm install <версия>` — своими
  строками таблицы решений (факт `push_node_pinned`, ход `install_node`), а без решателя (node в
  `PATH` нет или она старая) говорят строку сами. Git-хук отказывает до строки о числе шагов; набор
  вперёд кончается кодом 3.
- Сценарии SC-AK-1846, SC-AK-1847 в `docs/specs/agent-kit/push-gate-ahead/`.

## Что решили и почему

- **Одна функция на три места.** Перемер перед PR уже ставил закреплённую node своим кодом; теперь
  набор, набор вперёд и перемер берут её из одной функции и не расходятся на одной ветке.
- **Более новая node той же главной версии годится.** Отказ при точном пине и установленной 22.23
  требовал бы совпадения до патча, хотя `engines` дерева её принимает.
- **Node другой главной версии отказана.** Так записано в одобренном плане; отказ называет команду,
  которая его снимает.
- **PATH хука вне набора не меняется.** Отказы, чтение доски и разметка идут на node хука; красный
  набор без решателя на старой node проходил и до задачи — это находка рядом с планом эпика.
