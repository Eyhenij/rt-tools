# RT-3220 — выкатка убирает кэш сборки, у правила о зависимостях есть проверка

Задача RT-3220 эпика RT-3227, ветка `RT-3220-deploy-cache-cleanup`, 12–13.11.2026. Ветка взята от
ветки эпика после слияния RT-3219 (PR #3263). Папка `docs/tasks/RT-3220-deploy-cache-cleanup/`
разобрана в эту запись.

## Просьба

Слово владельца об эпике: «заведи новый эпик на актуализацию обвязки agent kit и разбей на задачи.
нужно сделать ревизию всей документации, правил и скилов в agent kit. так же нужно начать с
построения графа graphify для каждого из проектов в этом репозитории, если это будет необходимо -
построить некое подобие графа для понятий и правил в agent kit». Как делить ревизию и когда править:
«По семьям законов, правки сразу». О том, в какой эпик идут эта задача и RT-3219: «Взять в эпик
RT-3227».

Вопрос владельцу был один: записывать ли срок ожидания свежей версии пакета в настройки установки.
Ответ: «Записать 1440 минут (Recommended)».

## Откуда задача

Ревизия семьи закона о поставке, RT-3194, нашла три места, где файлы привязок правил говорили
больше, чем делает дерево:

- сборка образов выкатки идёт на машине владельца и кэш сборки за собой не убирает;
- срок ожидания свежей версии в дереве не записан, действует умолчание pnpm 11;
- хук коммита форматирует каждый добавленный файл, а у правила `dependencies` нет ни одной проверки.

## Что сделано

- Скрипт `.github/scripts/prune-builder.sh` убирает кэш сборки, которым сутки никто не пользовался, и
  всё сверх десяти гигабайт. Его зовёт шаг уборки в конвейере проверок и отдельное задание выкатки
  после обеих сборок образов.
- В `pnpm-workspace.yaml` записано `minimumReleaseAge: 1440`. Число равно умолчанию pnpm 11,
  поведение установки не меняется.
- Хук `.husky/pre-commit` зовёт только `lint-staged`. Форматтер в нём берёт `js`, `mjs`, `cjs`, `ts`,
  `html` и `scss` в каталогах `apps`, `libs`, `projects` и `tools/eslint-rules`.
- Проверка `tools/check-dependencies.mjs` с тестом стоит в наборе перед отправкой и шагом конвейера
  проверок. Она отказывает в трёх случаях: диапазон версии в корневом `package.json`; срок ожидания
  не записан, равен нулю или записан дважды; форматтер перед коммитом берёт файлы вне каталогов и
  расширений линтера.
- Переписаны привязки трёх статей в файлах привязок правил `deploy-flow` и `dependencies`. Отчёт графа
  правил: раздел «Rules nothing executes» пуст.
- Приведены к правке тексты: `docs/PROD.md`, раздел дерева в паттерне `git-workflow-docker`, новый
  раздел дерева в правиле `dependencies`, комментарий и сценарий о журнале изменений.

## Решения

- Скрипт уборки лежит в `.github/scripts/`, а не в `deploy/`: каталог `deploy/` выкатка копирует на
  узел целиком, а сборщика на узле нет.
- Уборка в выкатке — отдельное задание после обеих сборок. Шаг внутри каждой сборки снимал бы кэш
  второго образа между сборками.
- Уборка в выкатке идёт по сборщику по умолчанию. Шаг сборки объявляет `message-bus-builder`, но
  журнал выкатки от 08.11.2026 печатает сборку через сборщик по умолчанию, и кэш именованного пуст.
  Первая версия правки убирала по имени и чистила бы пустое; это нашло второе ревью кода.
- Отказ уборки не делает запуск выкатки красным, при отмене запуска уборка не идёт.
- Форматтер привязан и к расширению, и к каталогу. Первая версия брала расширения по всему дереву;
  ревью показало, что вне `apps`, `libs`, `projects` и `tools/eslint-rules` запуска линтера нет.
- Шаблоны `html` и файлы, которые линтер пропускает по имени, оставлены форматтеру. Формат их
  линтер не проверяет, но без форматтера шаблоны остались бы без единого вида. Решение исполнителя,
  названо владельцу в описании PR.
- Правилу `dependencies` написана своя проверка: граф правил считает правило исполняемым только по
  файлу кода, названному в файле привязок, а настройка в манифесте таким файлом не считается.

## Чего работа не закрыла

- Признак задачи «файлы привязок больше не пишут „исполнено частично"» выполнен для `dependencies` по
  статьям о версии и сроке. Для `deploy-flow` — нет: файл привязок говорит, что статья об уборке исполнена
  только для кэша сборки. Образы выкатки с меткой sha и образы набора перед отправкой остаются на
  машине сборки, выкатка собирает не через объявленный сборщик. Это задача RT-3264.
- Ручная команда `pnpm run prettier` форматирует тексты под `projects`. Это задача RT-3265.
- Выкатка на этой ветке не запускалась: запуск делает владелец. Правило `deploy-flow` требует
  запустить правку выкатки до слияния, шаг назван в описании PR.
- Диапазоны в манифестах публикуемых пакетов проверка не читает: библиотека объявляет диапазоном, что
  она принимает от потребителя.

## Что изменится для работающих в дереве

- При коммите больше не форматируются `.md`, `.json`, `.yml` и файлы вне четырёх каталогов.
- Диапазон версии в корневом `package.json` останавливает отправку и запуск CI.
- В выкатке появилось задание на машине владельца, до десяти минут.

## Слияние без конфликта

Слово владельца: «Вливать только при конфликте». 12.11 `main` принят в ветку эпика без конфликта,
коммит `69807db32`, 20 коммитов: проверка поставки не даёт создать ветку задачи от базы без
последнего коммита `main`.

## Ревью

круг — на `5ca2e60cc`, правки `5868f49c0`. Второй — на `5868f49c0`, правки `8211632bd`. Оба круга шли
на модели Opus: обычная модель ролей отказала по лимиту на первом вызове.
