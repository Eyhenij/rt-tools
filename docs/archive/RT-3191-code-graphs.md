# RT-3191 — графы кода корня и каждого проекта в истории дерева

Задача RT-3191 эпика RT-3190, ветка `RT-3191-code-graphs` от ветки эпика `RT-3190-agent-kit-revision`,
11.11.2026. Папка `docs/tasks/RT-3191-code-graphs/` разобрана в эту запись.

## Просьба

Слово владельца: «заведи новый эпик на актуализацию обвязки agent kit и разбей на задачи. нужно
сделать ревизию всей документации, правил и скилов в agent kit. так же нужно начать с построения
графа graphify для каждого из проектов в этом репозитории».

Вопросы и ответы:

- **Как строить граф для проектов репозитория?** Варианты: один граф на репозиторий
  (рекомендованный), граф на каждый проект, оба. Ответ: «Оба варианта».
- **Класть ли граф в историю?** Варианты: в `.gitignore` (рекомендованный), коммитить `graph.json`.
  Ответ: «Коммитить graph.json».

Весь разбор эпика лежит в `docs/plans/agent-kit-revision.md`.

## Что сделано

- `npm run graph:build` строит граф корня и граф каждого каталога под `projects/`, `apps/` и
  `libs/`, всего 27. Строит `graphify update` без языковой модели.
- В историю идёт только `graph.json`. Кеш, отчёт, страница и манифест игнорируются.
- Две ветки с разными графами сливает драйвер `graphify merge-driver`. `.gitattributes` называет его,
  а команду в конфиг копии пишет шаг установки `prepare`.
- Графы не считаются входом проектов nx (`.nxignore`) и не форматируются prettier.
- Дерево называет признак `graph`. Раскладка кладёт шаблон `task-flow-graph`, а надстройка дописывает
  к нему то, что есть только здесь: 27 графов, свою команду сборки и чтение `built_at_commit`.

## Решения

- **Проект здесь — каталог под `projects/`, `apps/` и `libs/`, а не проект nx.** Владельца об этом
  не спрашивали, решение принял исполнитель. Каталог под `libs/` держит до 53 проектов nx и получает
  один граф. Проект nx `tools/eslint-rules` своего графа не получил и есть только в графе корня.
- **Правила игнорирования вошли раньше графов.** Хук pre-commit прогоняет prettier по каждому файлу
  в индексе и переписал бы 40 МБ JSON.
- **nx не видит графы через `.nxignore`, а не через `namedInputs`.** Граф корня не лежит ни в одном
  корне проекта, а каталог `libs/` держит несколько проектов. Одна строка закрывает оба случая.
- **Граф — не предмет тяжёлых проверок перед push.** Роль `product-strategist` до PR доказала:
  `rt_push_touched` относил граф корня к `everything`, а граф проекта — к предмету проекта. Каждая
  пересборка поднимала бы два набора e2e, оба набора снимков и сборку образов, а проверка покрытия
  e2e не пускала бы PR. Теперь `graphify-out/` стоит в своей ветке выше предметов. Сценарий в
  `tools/tests/push-heavy-subjects.test.sh` на старом коде получает `everything`.
- **Проверки дерева не заходят в `graphify-out`.** Первый прогон набора перед push покраснел:
  `check-lib-layers` прочёл кеш графа внутри `libs/` как либу без слоёв, а `check-reuse` — страницу
  графа как разметку экрана. Каталог добавлен в список того, что проверки обходят, в источнике
  пакета, и обход либ теперь берёт тот же список.
- **Из id узлов вырезан путь копии.** graphify строит id узлов скриптов `.sh` из абсолютного пути:
  352 таких id в графе корня и 230 в графе `projects/agent-kit` несли домашний каталог и имя копии
  в публичную историю. Пересборка в другой копии переписывала бы их, а слияние давало дубли. Это
  тоже нашла роль. Команда сборки вырезает этот префикс; совпадений id после этого нет.
- **Перед сборкой прежний `graph.json` удаляется.** `graphify update` сливает новое с графом на
  диске: id в графе уже без пути копии, у свежей выборки — с путём, и каждый узел скрипта
  оказывался дважды. Кеш выборки остаётся, поэтому сборка не дольше. По той же причине каждый граф
  получает метку текущей головы: прежде graphify оставлял граф с неизменной топологией нетронутым,
  со старым `built_at_commit`.
- **У файлов в корне графа корня id начинаются с `root_`.** graphify ставит перед ними имя каталога:
  в графе проекта это имя проекта, в графе корня — имя копии, и оно разное у каждой копии.
- **`built_at_commit` называет родителя коммита, который несёт граф.** Граф строится с головы и
  входит в следующий коммит. Надстройка шаблона говорит, как это читать.
- **Драйвер слияния убирает `built_at_commit`.** Слитый граф не собран ни с одной головы, и шаблон
  читает его как устаревший. Это верный ответ, а не потеря.
- **GitHub свои драйверы слияния не запускает.** Если граф пересобран в обеих ветках, кнопка
  слияния на странице PR покажет конфликт в `graph.json`. Его снимают на машине: слить базу в
  ветку и пересобрать граф командой `npm run graph:build`. Стопка веток эпика этого избегает:
  каждая следующая ветка уже несёт граф предыдущей.
- **Без graphify на машине слияние графов даёт конфликт.** Драйвер — внешняя программа на Python, через
  npm её не поставить. Шаг установки только пишет команду в конфиг git.

## Цена

Полная сборка — 132 с. 27 графов весят 67 МБ, граф корня — 41 МБ, после gzip 2,1 МБ. Примерно столько
история прибавляет на каждую пересборку корня, которая попала в коммит, плюс графы проектов.

## Проверено

- `git ls-files '*graphify-out/graph.json' | wc -l` — 27, у каждого `built_at_commit`.
- `git status --short -uall` после сборки показывает из `graphify-out/` только `graph.json`.
- `nx show projects --affected --files=<27 графов>` — `[]`.
- Пробное слияние `git merge-tree` двух веток, каждая добавляет узел в один граф: маркеров
  конфликта нет, в результате оба узла.
- `pnpm run agent-kit:check` — разложенное сходится с пакетом.
