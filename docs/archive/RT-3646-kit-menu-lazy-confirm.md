# RT-3646 — диалог подтверждения menu грузится при первом подтверждении

Задача RT-3646 эпика RT-3641, запись от 2026-11-26. Прежний адрес:
`docs/tasks/RT-3646-kit-menu-lazy-confirm/`.

## Просьба владельца

> Выпуск `@rt-tools/ui-kit-v2` 0.52.0 заметно тяжелее 0.51.0, и два потребителя вышли за бюджет стартового пакета. Задача: найти, что утяжелило части кита, и вернуть вес без потери возможностей 0.52.0.

Затем владелец одобрил эпик («запускай task flow») и вёл задачи словами «Влил, дальше». План задачи одобрен ответом в меню: «Одобряю».

## Согласия владельца

Вид и поведение диалога не меняются: меняется момент загрузки его кода.

- **Без вида:** «Одобряю»

## Что сделано

- Пункт меню не импортирует диалог подтверждения статически: `import type` для типа и ленивый `import()` при первом подтверждении. Состояние загрузки лежит в `rt-menu-confirm.code.ts`: все пункты страницы грузят кусок один раз.
- Сбой загрузки перехвачен внутри `mergeMap`: ошибка идёт обработчику ошибок приложения, пункт отвечает меню «не подтверждено», поток подтверждений живёт, следующее нажатие пробует снова. Бросивший сам обработчик ошибок поток не убивает.
- Пока подтверждение идёт, второй щелчок по пункту второго диалога не открывает (флаг `#confirming`: раньше второй щелчок закрывала подложка диалога, а до прихода куска её нет). Пункт, снесённый посреди подтверждения, отвечает меню «не подтверждено».
- Новая публичная функция `rtPreloadMenuConfirmDialog()` подгружает код заранее. Класс диалога из точки `menu` не экспортировался и не экспортируется.
- Тесты: 9 проверок ленивой загрузки (подтвердить, отмена, закрытие без ответа, повтор, второй щелчок, снос пункта, предзагрузка, отключённый пункт, пункт без вопроса) и 2 на сбой куска (`jest.mock`, обработчик ошибок, бросающий сам). Тесты меню и тест приложения `admin-invites-list.component.spec.ts` подгружают код диалога до жеста.
- Живая проверка в закреплённом Chrome на витрине: до щелчка 20 скриптов, кусок диалога не запрошен; первое подтверждение запросило один кусок, диалог показан, «Отмена» закрыла его; повторное подтверждение без нового запроса, «Подтвердить» закрыла диалог и меню.

## Что решили и почему

- **`mergeMap` остался.** План обещал порядок подтверждений без перемен; флаг `#confirming` не даёт второму подтверждению начаться за время загрузки, как раньше не давала подложка.
- **Функция предзагрузки публична.** Приложениям и их тестам, которые нажимают на пункт и сразу ищут диалог, нужно ждать код; так упали два теста приложения. Выпуск минорный.
- **Вес набора упал больше, чем часть menu, из-за `button`.** Часть menu 39659 → 35212 (−4,4 КБ); из набора ушла часть `button` (7098), единственным, кто тянул её на старт, был диалог. Потребитель, который сам использует кнопку, выигрывает около 4,4 КБ.

## Что не сделано

- Цель по весу меряется на наборе сторожа: набор 331452 → 320477, gzip 57656 → 56404 (до слияния листа popover); после слияния ветки эпика порог пересчитан: 327809 → 316864, gzip 58419 → 56403. Сравнения с весом 0.51.0 нет: это уровень эпика.
- Сторож веса читает готовую сборку без проверки свежести; задача отдельная.
- Размер куска диалога и задержка при медленной сети в сборке потребителя не мерялись; обрыв сети вживую не проверялся, сбой держит тест.
- Меню, закрытое за время загрузки куска, диалог откроет после прихода кода (пункт жив до ответа).
- Находки разбора правил по RT-3645 лежат в `docs/plans/kit-presets-by-demand-rules-review-3645.md` и ждут слова владельца.

`pnpm exec nx test @rt-tools/ui-kit-v2` — все зелёные; `node tools/check-kit-weight.mjs` — «316864 байт при пороге 316864», часть menu 35320.
