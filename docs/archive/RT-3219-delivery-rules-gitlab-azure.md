# RT-3219 — правила поставки для GitLab и Azure приведены к варианту GitHub

Задача RT-3219 эпика RT-3227, ветка `RT-3219-delivery-rules-gitlab-azure`, 12.11.2026. Ветка взята
от ветки задачи RT-3196; после слияния RT-3196 в ветку эпика (PR #3224) в неё принята ветка эпика,
и запрос идёт в `RT-3227-agent-kit-revision-day1`. Папка
`docs/tasks/RT-3219-delivery-rules-gitlab-azure/` разобрана в эту запись.

## Просьба

Слово владельца об эпике: «заведи новый эпик на актуализацию обвязки agent kit и разбей на задачи.
нужно сделать ревизию всей документации, правил и скилов в agent kit. так же нужно начать с
построения графа graphify для каждого из проектов в этом репозитории, если это будет необходимо -
построить некое подобие графа для понятий и правил в agent kit». Как делить ревизию и когда править:
«По семьям законов, правки сразу». О том, в какой эпик идут эта задача и RT-3220: «Взять в эпик
RT-3227».

Шесть вопросов начала работы закрыты допущением: владелец в этой сессии много раз подряд брал
рекомендованный вариант, а тело задачи называет работу по пунктам.

## Откуда задача

Ревизия семьи закона о поставке, RT-3194, нашла шесть мест, где варианты правил для GitLab и Azure
беднее варианта GitHub или спорят со своими паттернами. Замер на вершине RT-3196:

- слово «epic» стояло в правиле `git-workflow` для GitLab 2 раза и для Azure 2 раза, слоя эпика не
  было;
- в `deploy-flow` у GitHub было 28 статей, у GitLab и Azure по 17;
- в образце описания запроса у GitLab и Azure было четыре раздела против шести у GitHub: не было
  таблиц точек и цели;
- у статьи закона о требовании перед необратимым шагом не было строки ни в одном правиле поставки.

## Решения

- Образцом взят вариант GitHub, статья переписана словами хостинга. Отвергнуто: одно общее правило
  на три хостинга — команды расходятся в каждой второй статье.
- Место под слой эпика освобождено сокращением статей до формулировок варианта GitHub. Отвергнуто:
  расщепление правила — оно меняет раскладку у деревьев, которые его уже поставили.
- Статья о требовании перед необратимым шагом записана в `deploy-flow`, во все три варианта: о
  выкатке и миграции без обратного хода говорит это правило, и место в нём есть.

## Что сделано

- В `git-workflow` для GitLab и Azure добавлен слой эпика: эпик, ветка эпика и запрос эпика в
  таблице названий; ветка задачи от ветки эпика; база запроса; стопка веток и порядок слияния;
  карточка эпика. Схема хода работы заменена схемой с эпиком.
- Там же две статьи: запрос, на который конвейер не запускается, открывается готовым; слияние
  нажимает человек.
- Девятнадцать статей этих двух правил сокращены до формулировок варианта GitHub. Убраны доводы и
  описания случаев. Два указания при сокращении потерялись, их нашло ревью, они возвращены.
- В `deploy-flow` для GitLab и Azure добавлены четыре статьи: что несёт образ, запись о поломке
  прода, отсрочка проверки правки выкатки только словом владельца, на какие запросы запускается
  конвейер.
- Во все три варианта `deploy-flow` добавлена статья о кнопке слияния и ручном запуске выкатки:
  требование ставится на хостинге или называется тому, кто нажимает. Вариант GitHub разложен в это
  дерево, поэтому в компаньон `.claude/skills/deploy-flow/implementation.md` добавлена строка
  статьи с пометкой «Not checked».
- В образцах описания запроса для GitLab и Azure шесть разделов, как у GitHub.

Запас до предела в 24 000 знаков: `git-workflow.azure` — 23 621, `git-workflow.gitlab` — 22 459.
Задачи RT-3261 и RT-3262 добавляют текст в эти же файлы.

## Ревизия ролью и правки по ней

Роль `rules-reviewer` прочла три варианта правил и паттерны запроса и назвала 19 находок.
Исправлено:

- На Azure проверка не запускается на черновике, а правило велело открывать черновик и ждать
  запуска CI. Теперь запрос, который ждёт только запуска CI, открывается готовым.
- Статья о запуске CI для Azure отправляла искать ответ в файл конвейера, а он лежит в политиках ветки.
- Образцы команд открытия черновика не называли целевую ветку: запрос уходил в `main` мимо эпика.
- Строка стопки для Azure ссылалась на запрос знаком `#`, которым там называют рабочий элемент.
- Список паттернов называл слияние `main` в ветку задачи; отставание ветки считалось от `main`.
  Теперь везде база ветки.
- Вызовы стопки веток для каждого хостинга добавлены в паттерны запроса: общий паттерн стопки
  называет только вызовы GitHub.
- Строка связи при цели не в `main` показана образцом; о карточке эпика сказано, что её не читает
  ни одна проверка.
- В правилах GitLab «PR» заменён на «MR», в правиле Azure «task» — на «work item».

## Первый круг ревью PR

Четыре роли прочли ветку на вершине `2a275f479`: ревью кода, `project-manager`,
`product-strategist`, `goal-critic`. Исправлено:

- Список перед открытием запроса в образце Azure снова велел открывать черновик и ждать запуска CI —
  абзац был перенесён из текста GitLab.
- Команды `az repos pr update --target-branch` нет: у клиента нет такого флага. Перенос базы
  записан вызовом REST.
- Образец строки связи для Azure обещал закрытие рабочего элемента при слиянии эпика, а его там
  ничто не закрывает. Теперь элемент закрывается при завершении запроса, отметкой в окне Complete.
- Образец GitLab «закрывается рукой» шёл без строки `Closes`, которую тот же паттерн называет
  обязательной.
- Строка компаньона о новой статье говорила больше, чем делает проверка: она ищет только заголовок
  «Оставшийся шаг» и только в теле, переданном командой открытия.
- Возвращены два указания, потерянных при сокращении: временный каталог не годится для общего пути;
  обе стороны сравнения берутся от `origin/`.
- Для Azure объявлено отступление от закона: запрос, который ждёт запуска CI, открывается готовым, а
  закон держит такую работу черновиком. Причина — на черновике запуск CI там не запускается.
- В образец Azure добавлен предел описания запроса в 4000 знаков.

## Второй круг ревью PR

Те же четыре роли и повторный проход `rules-reviewer` на вершине `72e431fb7`. Исправлено:

- В текстах Azure снятие черновика и просьба о слиянии шли одним ходом, хотя запуск CI там начинается
  только после снятия. Теперь слияние просят после зелёного запуска CI. Пункт списка об «оставшемся
  шаге» называет запуск CI, а не «шагов не осталось».
- Порядок переноса базы на Azure был назван по-разному в правиле и в паттерне. Везде: до завершения
  нижнего запроса, потому что завершение удаляет ветку, в которую смотрит верхний.
- В образце Azure стояли две разные строки связи. Осталась одна, отметка окна Complete названа в
  разделе «Оставшийся шаг».
- Абзац о проверке базы в обоих правилах говорил, что дерево может дать и помощник очереди, и чтение
  флага. Чтение флага — код пакета, дерево его дать не может. Теперь сказано как есть: проверка
  читает базу только из `--base`; без помощника очереди она судит ветку по `main`, с помощником
  отказывает законному запросу в ветку эпика; до правки пакета за базой следит исполнитель.
- После вызова REST добавлено перечитывание базы запроса: клиент находит ресурс по имени.

## Чего работа не делала

- Закон не правился.
- Хуки и проверки не трогались. На GitLab и Azure проверки поставки базу от ветки эпика не держат:
  `git-guard-delivery-epic.sh`, `git-guard-delivery-folder.sh` и `git-guard-delivery-pipeline.sh`
  читают только флаг `--base`, а помощник очереди пакет несёт только для GitHub. Правила говорят
  это прямо, код — задача RT-3261.
- Сверка трёх вариантов за пределами шести пунктов задачи — RT-3262. Туда же ушло то, что роль
  `rules-reviewer` назвала необязательным: имя кнопки «Merge when pipeline succeeds», форма ссылки
  коммита `AB#` в правиле Azure, статья о готовом запросе с одним случаем из двух, слова другого
  хостинга в текстах Azure.
- Команды `glab` и `az` на хостинге не запускались: дерево живёт на GitHub. Флаги сверены с
  исходниками установленных клиентов. Вызов REST для переноса базы на живом проекте не проверен.

## Слияния без конфликта

Слово владельца: «Вливать только при конфликте». 12.11 сделано два слияния без конфликта, оба по
отказу проверки поставки:

- `main` принят в ветку эпика, коммит `d3961ff60`: без последнего коммита `main` в ветке эпика
  проверка не давала создать ветку задачи;
- ветка эпика принята в ветку задачи, коммит `72e431fb7`: без неё проверка не даёт открыть запрос.
  Файлов это слияние не меняло.
