# Grill

## The owner request

> изучи как утроен логин на <двух приложениях владельца> - нужно вынести логин в отдельный модуль который можно подключать в приложения

Имена приложений в файлы репозитория не пишутся; здесь они — «приложение А» и «приложение Б».

## What the tree already has

- Вход админки приёмника: интерфейс `libs/message-bus-admin/auth/` (форма, первый запуск, хранилище
  сессии на `BaseAsyncStoreService`, проверка маршрута, перехват истёкшей сессии, доступ к
  разделам), сервер `libs/message-bus-api/accounts/` (хэш пароля, пауза после неудачных попыток,
  сессионная cookie без доступа скриптов, роли, первый запуск). Описания —
  `docs/specs/message-bus/admin-auth/`, `docs/specs/message-bus/access-rights/`.
- Публикуемые пакеты: `projects/core`, `projects/store`, `projects/utils`, `projects/ui-kit-v2`;
  у второго кита есть стили экрана входа.

## Приложение Б (исследовано)

- Интерфейс: слои util ← api ← data-access ← ui ← feature ← shell. Сессия — пара токенов в
  localStorage (`StorageService` из `@rt-tools/core`), обновление одним запросом на все вкладки,
  Connect-перехватчик `Authorization: Bearer`, повтор после обновления; форма входа на компонентах
  второго кита; проверки маршрутов; разводка после входа по роли.
- Сервер: Connect-процедуры Login/Refresh/Logout, argon2, jose HS256 (доступ 15 мин), непрозрачный
  refresh-токен с хэшем и ротацией в базе, перехватчик вызывающего, декораторы доступа и реестр
  процедур с проверкой прав при старте.
- Завязано на приложение: модель организаций и «оператора платформы» в сессии, токене и контракте;
  пути после входа; ключ хранилища, заголовок, тексты без перевода; прямые запросы Prisma.
- Пробелы: нет «кто я», нет ограничения попыток, токены доступны скриптам страницы.

## Приложение А (исследовано)

- Две системы входа: сотрудники админки (почта и пароль, токен на 12 часов, без продления и
  без выхода на сервере) и гости сайта (ссылка или код, пароль, Google/Apple, токен на 90 дней
  со скользящим продлением). Общий секрет, различаются полем `aud`.
- Интерфейс: токен в localStorage (`StorageService` из `@rt-tools/core`), проверка маршрута с
  разбором срока токена на клиенте и возвратом на исходный адрес, Connect-перехватчик Bearer и
  выход на вход при `Unauthenticated`, хранилище «кто я» с правами `resource:action`, скрытие
  пунктов меню по правам, сброс хранилищ сессии одним хуком при выходе, переводы через Transloco.
- Сервер: scrypt, jose HS256, «кто я» с чтением базы на каждый вызов, закрытые по умолчанию
  декораторы доступа (ровно один на процедуру, проверка при старте), ограничение попыток по почте
  и адресу, одинаковое время ответа для несуществующей почты, восстановление и смена пароля,
  подтверждение почты, приглашения.
- Завязано на приложение: организации, членство, оператор платформы, приостановка, демо, тариф,
  поля «кто я» о первом объекте; пути `/login`, `/choose-organization`; заголовок и ссылки экрана.

## What the rules already say

- `reuse-first`: готовое не пишется заново; общий кусок живёт в общем слое.
- `lib-layers`: деление на слои и границы импорта.

## Analysis so far

- Сессия: токен в localStorage отпадает (доступен скриптам, нет настоящего выхода). Свой модуль —
  короткий токен в памяти и токен обновления в cookie без доступа скриптов; готовый сервис входа —
  его сессия.
- Права: общий слой при любом варианте — `resource:action`, ровно один декоратор доступа на
  процедуру, проверка при старте, скрытие пунктов меню. Варианты различаются тем, где живут
  пользователи: в каждом приложении, в своём общем сервисе или в готовом сервисе.
- Zitadel: Go, Postgres, AGPL с v3 (без изменений самого сервиса обязательств нет), организации в
  основе модели, Session API позволяет свои экраны входа и регистрации. Keycloak: Java, Apache 2.0,
  организации с версии 26, свои экраны — темой (FreeMarker или Keycloakify, который собирает тему из
  Angular-компонентов, то есть можно из кита), прямую передачу пароля OAuth 2.1 убирает.
- Приложение В (архивное, на Keycloak 21): вход по OIDC с перенаправлением (`keycloak-js`), экраны
  входа — тема Keycloak на FreeMarker и Tailwind, своего Angular-экрана нет. Токены только в памяти,
  сессия восстанавливается тихой проверкой SSO, конфигурация области хранится как код, вход только по
  приглашению через обязательные действия (подтвердить почту, задать пароль, принять условия),
  двухфакторный вход TOTP или кодом на почту. Страница входа выглядит в стилях приложения (поправка владельца: «страница логина на [приложении В] выглядит в стилях приложения»), но стили темы держатся отдельно от кита, на Tailwind. Беды:
  пять своих расширений на Java, одно из них выдаёт токен смены пароля без проверки, кто спрашивает;
  смена пароля в приложении без проверки текущего; нет обработки 401.
- Совет на сегодня: Zitadel + свои экраны на ките; пробный стенд первым шагом.

**Какой сервис входа берём, если оба позволяют экраны из нашего кита?**
«Keycloak + Keycloakify (Recommended)»

## Decisions

- **Сервис входа — Keycloak, экраны входа — тема через Keycloakify из компонентов второго кита.**
  Вход идёт штатными шагами Keycloak, своих расширений на Java не пишем. Отклонены: Zitadel
  (AGPL, шаги входа ведёт наш сервер), свой сервис, библиотека без сервиса (нет одного входа во
  все админки).
- **Модуль — три части:** Angular-пакет (вход через OIDC с PKCE, токены только в памяти,
  восстановление сессии, обработка 401 с одним повтором, проверки маршрутов, скрытие пунктов по
  правам), пакет для NestJS + Connect (проверка токена по открытым ключам, закрытые по умолчанию
  декораторы доступа, каталог прав с проверкой при старте), пакет темы Keycloakify. Плюс конфигурация
  области Keycloak как код.
- **Первая версия:** почта и пароль, смена и восстановление пароля, приглашения и подтверждение
  почты, Google/Apple.

- **Права живут в Keycloak.** У каждой админки свой клиент с ролями `resource:action`; права
  назначаются в Keycloak и приходят в токене. Каталог прав админка объявляет декораторами и
  выгружает в Keycloak; проверка при старте сверяет каталог с ролями клиента.
- **Организации — модель приложения** (владелец без предпочтения, взят рекомендованный вариант):
  модуль даёт точку подключения «текущая организация», организации и членство остаются в базах.
- **Один Keycloak на все приложения**, отдельный узел или контейнер со своим Postgres; один вход во
  все админки.
- **Эпик rt-tools — только модуль и стенд Keycloak.** Перевод приложений А и Б — отдельная работа в
  их репозиториях после модуля, с переносом хэшей паролей.
