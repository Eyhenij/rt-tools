# Пакет правил улучшается по метрикам приложений

**Эпик:** RT-3151 · **Ветка эпика:** `RT-3151-agent-kit-metrics`

## Что даёт

Владелец видит на одном экране главное число «Принято с первого раза» и причины его движения по приложениям. Каждая правка пакета называет метрику, которую должна сдвинуть, а следующий отчёт показывает итог. Сегодня правки идут из мнения, и помогла ли правка, неизвестно.

Слова владельца дословно лежат в разборе задачи RT-3152 и после неё в её записи архива.

## Точки

- **A:** наблюдения пишутся и уходят в приёмник командой человека. Раздел «Использование» показывает загрузки и отказы. Итога задачи и потерянных минут нет, метрики не названы.
- **B (RT-3152):** `agent-kit metrics` печатает отчёт по дереву. Признак: числа отчёта совпали со счётом по файлам наблюдений.
- **B (RT-3153):** отчёт показывает «Принято с первого раза» и «Пустые запуски». Признак: значение с путём или текстом в наблюдение не попадает.
- **B (RT-3155):** приёмник хранит новые числа. Признак: старая и новая запись приняты, повторная отправка дня не меняет итог.
- **B (RT-3154):** данные приходят без команды человека. Признак: без адреса и токена запрос не уходит, проверка при выключенной сети не задерживается.
- **B (RT-3156):** раздел «Качество» в админке. Признак: все состояния проверены на ширинах 1440, 768 и 375.
- **B (RT-3157):** правка пакета называет метрику. Признак: шаблон выпуска требует метрику.
- **G (веха эпика):** пакет готов улучшаться по числам. Признак: эпик влит в main, приёмник выкачен, пакет выпущен, отчёт собирает данные подключённых приложений.
- **После эпика (RT-3158):** первая правка по отчёту, отдельной задачей после двух недель данных. Признак: следующий отчёт показывает, сдвинулось ли число. Срок: примерно четыре недели от выпуска.

## Как стоят ветки

Ветка эпика отведена от главной, ветки задач идут стопкой: каждая следующая от предыдущей, PR по той же цепочке. Первая задача отведена от ветки эпика. Порядок нужен, потому что каждая задача читает данные предыдущей.

## Состав

| #   | Задача                                            | Состояние |
| --- | ------------------------------------------------- | --------- |
| 1   | RT-3152 — метрики описаны, отчёт по своему дереву | впереди   |
| 2   | RT-3153 — минуты, итог задачи, правки владельца   | впереди   |
| 3   | RT-3155 — приёмник хранит новые числа             | впереди   |
| 4   | RT-3154 — проверки и конец сессии отправляют сами | впереди   |
| 5   | RT-3156 — раздел «Качество» в админке             | впереди   |
| 6   | RT-3157 — правило цикла и метрика в выпуске       | впереди   |

Приёмник стоит раньше отправки: иначе приложения начнут слать запись, которую он не принимает.

RT-3158 вынесена из эпика: она ждёт данные с боевого приёмника, а выкатка идёт только из main. Владелец выбрал «Вынести RT-3158 из эпика (Recommended)». После RT-3157 порядок такой: PR эпика в main, выкатка приёмника, выпуск пакета, обновление приложений, две недели данных, RT-3158.

Договорённость вливается в описание пакета последним коммитом RT-3157. Проверка требует влитую договорённость только у PR в main: владелец выбрал «Поправить проверку (Recommended)».

Метрики ролей и команд входят в RT-3153: владелец выбрал «В этом эпике (Recommended)».

В RT-3153 также входит то, что договорённость требует, а отчёт RT-3152 пока называет словами «нет данных»: объявление проверкой своего правила, запись итога экзамена, знаменатель доли правок и функция `rt_pull_outcomes` со значением по умолчанию для GitHub. Признак RT-3153 и RT-3154 дополняется: число пришло от настоящего дерева.

## Находки RT-3155

- RT-3154: приёмник судит имя ресурса только по форме. Слово вида `ruleLoads:имя-клиента` он примет,
  поэтому имена по списку пакета оставляет отправитель, а своё пишет постоянным словом.
- RT-3154: новая строка замещает день целиком. Отправитель собирает окно из файлов, и пустая или
  урезанная карта затрёт числа дня, если файлы уже сняты сроком.
- RT-3154: ключ `sendFault` несёт числовой код причины сбоя со следующей дошедшей строкой. Таблицу
  кодов задаёт отправитель. Дерево с отказанным токеном не шлёт ничего и читается как молчащее.
- RT-3154: новые знаменатели `refusalsWithRule`, `roleVerdicts:<имя>`, `guardCompared:<имя>`,
  `rulesLaidOut`, `sectionsTotal` отчёт дерева уже считает или берёт из файлов пакета в дереве.
- RT-3157: приёмник выкатывается раньше пакета, новый ключ на старом приёмнике отказывает всю строку.
- RT-3156: `Postmortem.resource` и `RecordTransition` уходят сюда, в карточке их нет.
- RT-3156: ключи только добавляются. Убранный ключ отказал бы всю строку дереву на старой версии.

## Находки RT-3153

- RT-3154 зовёт `collectOutcomes` как есть: чтение уже идёт от прошлого дня и различает причины обрыва.
- Настоящий путь проверка → метка → слияние → отчёт появится только после попадания хуков в main.
  PR задач RT-3155–RT-3157 пройдут раньше, поэтому отсчёт двух недель для RT-3158 начнётся позже.
- Событие `SubagentStop` проверено по описанию и по записям ролей. Первая сессия после попадания хука
  в main покажет настоящую форму: если приговоров нет, числа ролей считаются только по вызовам.
- Файл учёта и метки лежат в каждой копии отдельно. RT-3154 должна хранить учёт по общему каталогу
  git, как это делает запись запусков: иначе две копии посчитают одни PR дважды.
- PR, открытый вызовом REST, подписи не получает и считается как PR без передачи.
- Слиянием базы сейчас считается любой коммит с двумя родителями.
- PR эпиков входят в счёт PR без передачи: метка читается только у PR с подписью.

## Чего эпик не делает

- Киты и остальные пакеты: следующий эпик на том же подходе, слово владельца «Сначала agent-kit (Recommended)».
- Текст сообщений: с приложений уходят только числа.
- Цели до измерений: владелец называет их после двух недель данных.
- Сравнение людей между собой.
