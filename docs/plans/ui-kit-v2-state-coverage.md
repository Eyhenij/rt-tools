# Покрытие состояний `@rt-tools/ui-kit-v2`: витрина и документация

## Контекст

Витрина второго кита показывает 80 файлов историй, и в 79 из них ровно один экспорт `Default`.
Docs-страниц у компонентов нет вовсе. Чтобы увидеть `outlined` + `warning` + `disabled`, надо
открыть `Button` и выставить три контрола руками — расхождение, видное только при таком
сочетании, не видит ни автор правки, ни ревьюер.

Задача: довести витрину до состояния, где все состояния каждого компонента видны сразу, и
записать это требованием, а не устной договорённостью.

Замеры на 2026-08-06: 94 компонента и директивы в 71 папке; 14 компонентов без историй
(`UI-KIT-V2-ISSUES.md` §2.1); 10 историй рисуют пустой массив (§2.3); 11 папок, где спек меньше,
чем компонентов; 81 спека; 72 покомпонентных `CONTEXT.md` плюс индекс.

Требования записаны и лежат рядом — этот план только исполняет их:
`docs/adr/0002-ui-kit-v2-state-coverage.md` (решения и их цена),
`.claude/rt-kit/overrides/laws/verifiability.md` (раздел «Демонстрация видимого состояния»),
разделы про `ui-kit-v2` в `.claude/skills/rt-tools-storybook/SKILL.md` и
`.claude/skills/rt-tools-testing/SKILL.md`.

## Что считается сделанным

Компонент покрыт, когда **каждая ось входов показана всеми значениями**, а не когда существует
контрол, которым до значения можно доехать. Перемножаются только оси, которые видно влияют друг
на друга (`theme × appearance` — да, `size × theme` — нет). Полный декартов продукт отвергнут:
у `Button` это 1296 ячеек.

## Волны 1–5 — по типам компонентов

Порядок: атомы (~15) → форменные (~12) → оверлеи (13) → составные (~20) → остаток и 14 без
историй. Внутри волны первым идёт компонент с самой богатой матрицей — на нём обвязка либо
выдержит, либо сломается дёшево. В волне атомов это `Button` (9 входов, 6 тем × 3 appearance).

### Повторяемый приём на компонент

Показан на `button`; для остальных те же файлы с другими именами.

| Файл                                                       | Что в нём                                                                                                                                                       |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `button/CONTEXT.md`                                        | без изменений, кроме снятой строки «Проверки» (волна 0)                                                                                                         |
| `button/Overview.mdx`                                      | новый: назначение, когда применять и когда нет, таблицы осей, таблица состояний, доступность, оформление, связанные компоненты, таблица входов и выходов руками |
| `button/stories/button.stories.ts`                         | `Default` переименовывается в `Playground`, args и argTypes остаются                                                                                            |
| `button/stories/button-matrix.stories.ts`                  | новый: по истории на ось + `States` + `Themes`                                                                                                                  |
| `button/stories/component/test-button-matrix.component.ts` | новый: `@switch (part)` по осям; истории выбирают ветку значением `part` в `args`                                                                               |

Обёртка матрицы нужна всегда, а не «только если ось не выражается конфигом обвязки»: истории по
оси должны быть отдельными записями в боковике, а Storybook переключает ветку шаблона входом.
Обвязка `src/showcase/` рисует сетку и ряд, но выбор, что показать, живёт в обёртке.

Правила, решающие содержимое матрицы:

- Ось показывается всеми значениями сразу и подписывается.
- Оси перемножаются, только если видно влияют друг на друга.
- Ось, которую показать нельзя, объявляется в `Overview` с причиной — молчаливый пропуск
  выглядит как покрытие.
- Историю с пустым набором данных считать непокрытием: десяти компонентам (`rt-table`,
  `rt-chat`, `rt-calendar`, `rt-bar-list`, `rt-night-grid`, `rt-thread-list`, `rt-timeline`,
  `rt-toggle-button-group`, `rt-filter-control`, `rt-split-button`) сначала заводится
  правдоподобный набор, потом матрица.

### Волна 1 — атомы · сделана

15 компонентов: `[rtButton]`, `rt-icon`, `rt-spinner`, `rt-skeleton`, `rt-skeleton-wrapper`,
`rt-tag`, `rt-live-badge`, `rt-info-item`, `rt-stat-tile`, `rt-delta-view`, `rt-icon-button`,
`rt-logo`, `rt-theme-toggle`, `rt-download-link`, `rt-empty-state`.

Что волна добавила к обвязке — остальным волнам это уже готово:

- `src/showcase/story-states.ts` — состояния взаимодействия и параметр `pseudo`. Признак
  `data-story-state` вешается на элемент атрибутом, а не классом: `[class]`-привязку у половины
  кита занимает `@HostBinding('class')` самого компонента. Если стилизован не хост, а контрол
  внутри шаблона (`<button>` в `rt-icon-button`), в `storyPseudoParameters()` передаётся спуск
  до него.
- Тёмная половина `story-themes` несёт и признак `data-theme`: правила вида
  `[data-theme='dark'] .rt-…` без него в половину не попадают.

Что разошлось с планом:

- **Страж таблиц пришлось сузить до раздела «Входы».** Он читал первую колонку любой таблицы
  страницы, а на странице стоят ещё таблицы осей, состояний и выходов — значение оси `primary`
  числилось бы входом, которого в компоненте нет, и `verify` падал бы на исправном документе.
- **Пара «светлая ↔ тёмная» показывала две одинаковые колонки**, пока тулбар стоял в тёмной
  теме. Светлые назначения вынесены в миксин `rt-theme-light-tokens` по образцу тёмных, обе
  половины прибивают набор явно. Остаточная оговорка: при тёмной теме в тулбаре светлая
  половина получает светлые свойства, но правила `[data-theme='dark'] …` продолжают доставать
  её от `<html>` — снять их изнутри нечем, светлую половину смотрят при светлой теме.
- **Тайпчек расширен на истории и обвязку** (`tsconfig.spec.json`): до этого их проверяла
  только полная сборка витрины. Шаблоны он всё равно не проверяет — несуществующее имя иконки
  в матрице поймала витрина, а не команда. Проверка шаблонов остаётся за `build-storybook`.
- **`rt-logo` показан безымянными заглушками начертаний.** Своих кит не везёт, и без
  подставленных свойств каждая ячейка была бы пустым местом нужного размера. Настоящий логотип
  в витрине увидеть нельзя — это записано в его `Overview` как отсутствие предмета.
- **Пустые истории нашлись не только в списке §2.3.** Правдоподобный набор пришлось завести
  ещё `rt-delta-view` (рисовал пустоту при `delta: null`) и `rt-info-item` (значение приходит
  проекцией, а обёртка ничего не проецировала).

Дефекты кита, вскрытые матрицами: у `rt-download-link` не было ни наведения, ни видимого
фокуса — кнопка нарисована ссылкой, и умолчательный контур браузер снимает вместе с рамкой.

### Волна 2 — форменные · сделана

13 компонентов: `rt-field`, `rt-input`, `rt-textarea`, `rt-input-number`, `rt-checkbox`,
`rt-toggle-switch`, `rt-counter`, `rt-counter-row`, `rt-date-picker`, `rt-file-input`,
`rt-filter-control`, `rt-toggle-button-group`, `rt-rich-editor`. Оверлейные поля (`select`,
`multiselect`, `autocomplete`) остались волне 3 — у них свой приём.

Что волна добавила к обвязке — остальным волнам это уже готово:

- **Ширина ячейки** — вход `slotWidth` у сетки и ряда плюс `showcase/story-metrics.ts`. Поле
  занимает всю ширину родителя, и в ячейке, растущей по содержимому, оно схлопывалось, показывая
  не размер, а его отсутствие. Ширина одна на все матрицы полей: разойдись она — соседние
  страницы показывали бы один контрол разной ширины, и разница читалась бы как его свойство.
- **Состояния разложены на отдельные значения** (`STORY_STATE_DEFAULT`, `…_HOVER`, `…_ACTIVE`,
  `…_FOCUS_VISIBLE`, `…_FOCUS_WITHIN`), а наборы собираются из них: `STORY_FIELD_STATES` —
  где рамку рисует коробка вокруг контрола (фокус ловится `:focus-within`),
  `STORY_CONTROL_STATES` — где рамку рисует сам контрол (`:focus-visible` со спуском до него).
- **Значение форменных приходит только формой.** Входа значения у контролов нет, его пишет
  `writeValue`, поэтому у каждой заполненной ячейки свой `FormControl`. Подсветка ошибки требует
  `markAsTouched()` заранее: она включается по `invalid && (touched || dirty)`, и без касания
  ячейка «ошибка» показывала бы исправное поле.

Что разошлось с планом:

- **Страж таблиц пришлось научить читать основу.** Половина входов поля объявлена не в его файле,
  а в `RtFormControlBase`; слитая с собственными, она выглядела бы объявленной здесь, а правка в
  основе меняет разом все страницы наследников. Такие входы описываются разделом «Входы от основы
  полей» и сверяются с основой. Заодно объявление входа теперь ищется в пределах строки: поле без
  присваивания (абстрактное `hasValue`) забирало себе `= input` следующего за ним входа, и тот не
  находился вовсе — на `rt-input` это вскрылось сразу.
- **Витрине пришлось подключить тему Quill** (`node_modules/quill/dist/quill.snow.css` в `styles`
  обеих storybook-целей). Кит ждёт её от приложения, а без неё редактор в витрине показывал то,
  чего не увидит ни один потребитель: тулбар без иконок и списки без маркеров.
- **Узкое представление `rt-filter-control` показано подменой службы брейкпоинтов** в декораторе
  истории: ширину окна витрины историей не задать, а второе представление выбирается по ней.
- **Пустые истории заведены не только у двоих из §2.3.** `rt-filter-control` и
  `rt-toggle-button-group` получили правдоподобные наборы вариантов, `rt-file-input` — настоящие
  `File` нужного размера, `rt-rich-editor` — модель Quill с выделением и списком.

Дефекты кита, вскрытые матрицами:

- **Отмеченного чекбокса и включённого тумблера на экране не бывало вовсе.** Оба стиля написаны
  как `&--мод &__элемент` внутри составного родителя (`rt-checkbox .rt-checkbox`), и второй `&`
  разворачивался в родителя целиком — в селектор, требующий чекбокса внутри чекбокса. Заливка
  отмеченного, прочерк смешанного, цвет трека и уезжающий бегунок не применялись с перехода кита
  на единую инкапсуляцию. Починено; элемент адресуется классом. Тех же двух уровней в ките больше
  нет — `rt-dialog` и `rt-aside` составные, но компаундов `&--мод &__элемент` у них не осталось.
- **`rt-rich-editor` не находился вмещающим полем.** Единственный наследник основы без алиаса
  `{ provide: RtFormControlBase, useExisting }`, а `rt-field` ищет контрол запросом по
  абстрактному классу — редактор в него не попадал, и обёртка молча теряла и звёздочку
  обязательности, и текст ошибки. Починено, поведение закреплено спекой.
- **Отключение редактора не видно, а режима чтения у него нет.** Quill перестаёт принимать ввод,
  но рамка и тулбар остаются прежними; `[readonly]` на `rt-field` он принимает и игнорирует.
  Не чинилось — объявлено в `Overview` с указанием, чем пользоваться вместо.

## Проверка

На каждой волне, до отметки «сделано»:

```bash
pnpm run check:all                              # lint + typecheck + test + build, все пакеты
pnpm exec nx run @rt-tools/ui-kit-v2:typecheck  # Jest типы не проверяет — эта цель проверяет
pnpm exec nx verify @rt-tools/ui-kit-v2         # таблицы входов в MDX сходятся с исходниками
pnpm run build-storybook:ui-kit-v2              # витрина собирается статикой
pnpm run agent-kit:check                        # законы не разошлись с пакетом
```

Затем — глазами, потому что закон требует показа, а не только зелёной сборки:
`pnpm run storybook:ui-kit-v2`, открыть `localhost:6007` и пройти каждый компонент волны
**в обеих темах**, сверяя, что каждая ось показана всеми значениями и ни одна ячейка не пуста.
Это единственная проверка, которую нельзя заменить командой.

Оговорка про порт: если 6007 уже занят чужим сервером витрины, команда спросит про запасной порт
и будет ждать ответа, а `curl` на 6007 всё это время отвечает — чужим сервером. Запускать свой
надо явным `nx run @rt-tools/ui-kit-v2:storybook --port 6009`, иначе правки конфигурации
(например, новый файл в `styles`) в браузере не появятся, а выглядеть это будет как их
бездействие.

Отдельно после волны 0: `nx build @rt-tools/ui-kit-v2` и убедиться, что в `dist/ui-kit-v2` есть
73 `CONTEXT.md` и нет ни одного файла обёртки.

## Открытые вопросы, вынесенные из объёма

- **Чем проверяется полнота матрицы.** Ось, забытая в матрице, выглядит так же, как ось с одним
  значением. `verify`-скрипт сверяет таблицу входов, но не то, что каждый вход показан сеткой.
- **Нужно ли сравнение снимков.** Матрица ловит расхождение, только когда на неё смотрят.
- **RTL.** Кит написан на логических свойствах, но ни одного `[dir=]` в нём нет, и поведение в
  правостороннем письме не проверено ничем. В объём не входит.
