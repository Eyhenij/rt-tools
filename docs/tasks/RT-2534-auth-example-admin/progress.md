## Decisions along the way

- Адрес области и имя клиента пример сервера берёт только из среды, без значений в коде: эти значения принадлежат стенду, а копия в коде повторяла бы тестовые значения пакетов (`check:dupes`).
- Тестовое имя клиента в двойнике Keycloak пакета `auth-angular` сменено на `double-admin`: прежнее совпадало с настоящим клиентом стенда, и `check:dupes` называл повтором настройки примера админки.
- Сквозной набор не снимает кадры и идёт браузером машины, а не браузером из образа. Из образа Keycloak и админка видны под другим именем хоста. Тогда издатель в токене не совпал бы с тем, которого ждёт сервер.
- Срок токена клиента примера — 40 секунд, полем клиента в файле области. Так обновление токена видно в одном тесте за 12 секунд ожидания.
- Ключи Google приходят из `deploy/auth/.env` или среды через compose. Нужны три переменные: `RT_GOOGLE_ENABLED=true`, `RT_GOOGLE_CLIENT_ID`, `RT_GOOGLE_CLIENT_SECRET`. Прежний ключ `IMPORT_VAR_SUBSTITUTION_ENABLED` config-cli не читал; верное имя — `IMPORT_VARSUBSTITUTION_ENABLED`.
- Два новых шага идут в наборе, когда ветка тронула модуль входа или второй кит: второй кит рисует экран входа темы и пример админки. Ручного запуска у CI нет, поэтому шаги впервые пройдут на PR эпика в main; их команды прогнаны на этой машине, она же раннер.
- Отметки «Not covered» у сценариев стенда остаются: проверка описаний считает тестом только `.spec.ts`. Причина в отметках переписана: проверка стенда уже стоит в наборе и в CI.
- Тема выпускается не в npm, а JAR в выпуске GitHub с меткой `rt-auth-keycloak-theme@<версия>`: Keycloak берёт тему из каталога `providers`. Порядок запуска публикаций: `auth-contract` уже в npm, дальше `auth-server`, `auth-angular`, `auth-import` и тема — в любом порядке.
