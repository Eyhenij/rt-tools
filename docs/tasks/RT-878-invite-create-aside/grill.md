# Разбор просьбы

## Просьба владельца

> изучи как приложение потребитель получает токен в apps/message-bus

> токены нужно выдавать из ui админки - заводи задчу по task flow

> пзидуй прикручивай асайд создания инвайта

## Что уже есть в дереве

Разведка командами по текущему дереву, 19 августа 2026 года.

**Как токен выдаётся сейчас — два пути, оба мимо админки.**

- Приглашение выдаёт команда строки запуска `tree:invite <имя>`
  (`libs/message-bus-api/trees/feature/src/lib/tree-commands.service.ts`). Код печатается один
  раз, в хранилище уходит только его хеш (`inviteCodeHash`), годен 48 часов (`INVITE_HOURS`).
- Дерево обменивает код на токен само: `agent-kit enroll --code <код>`
  (`projects/agent-kit/src/lib/enroll.ts`) зовёт `POST /api/intake/enroll`
  (`libs/message-bus-api/trees/feature/src/lib/enroll.controller.ts`) и кладёт токен файлом с
  правами `0600`. Операция публичная, сторожат её годность приглашения и ограничитель частоты —
  пять обращений в минуту на ключ клиента.
- Прямая выдача — команды `tree:add <имя> <признак>` и `tree:token <имя>`: печатают токен один
  раз, в базу кладут `treeTokenHash`. Отзыв — `tree:revoke <имя>`.

**Что админка умеет сегодня.**

- Раздел приглашений: `GET /api/invites` — страница с состоянием каждого, `DELETE
/api/invites/:имя` — отзыв годного (`invites-read.controller.ts`, экран —
  `libs/message-bus-admin/invites/feature/list`). Выдачи приглашения из интерфейса нет.
- `GET /api/trees` — деревья именами, только для выпадашки отбора над списками
  (`trees-read.controller.ts`). Своего раздела у деревьев нет вовсе.
- Прав внутри админки нет: операции закрыты входом человека (`SessionOperation`), вошедший
  видит всё.

**Готовый образец раскладки.** Раздел `invites` собран по семьям
`api / data-access / feature / shell / ui / util`, как и `proposals`, `postmortems`,
`summaries`; списочный экран собран общей основой списка.

## Что уже сказано в правилах

- Спек `docs/specs/message-bus/intake/spec.md`, раздел «Что не входит», прямо отказывает
  просьбе в её нынешнем виде: **«Заведение и отзыв токена дерева операцией запроса не
  делаются»**, «Отзыв токенов операцией запроса — дело команд строки запуска», «Перевыпуск
  токена самим деревом» не входит. Довод там же: операция перевыпуска становится вторым путём
  к токену.
- Тот же спек: «Имя дерева задаёт владелец при выдаче приглашения, а не обращение»; «У дерева
  годен один токен: новый замещает прежний»; «Ни приглашение, ни токен не попадают в
  наблюдения и логи».
- Спек `docs/specs/message-bus/admin/spec.md`: **«Раздела деревьев в админке нет вовсе»** —
  деревья живут выпадашкой отбора; «Кода приглашения на экране нет никогда»; «Пустой список
  называет команду, которой приглашение выдаётся»; «Вход создания записи на списочной странице»
  в раздел не входит и открыт вопросом `Q-27`.
- Закон доступа через правило `permissions`: вид доступа объявляется меткой, и он ровно один;
  публичная операция, заводящая запись, закрыта ещё и ограничителем частоты.

Отсюда: работа меняет обе договорённости — приёма и админки, — и это её предмет, а не побочный
след.

## Вопросы и ответы

Ругательства владельца в цитатах заменены многоточием в квадратных скобках; остальное дословно.

**Что именно должно выдаваться из интерфейса админки — приглашение, токен или и то и другое?**
«при чём тут вообще дерево? какого […] message bus должен что-то занть про деревья? что это за
уёюище? кто это реализовал?»

Ответ исполнителя фактами: «дерево» — слово словаря (`docs/GLOSSARY.md:124`), приёмник держит о
отправителе только имя и признак; всё сделано машинной учётной записью 14–17 августа 2026 по
спеку, влитому 14 августа (`16685979`, `4e239094`, `ea03f03b`, `bdc677a6`).

**Претензия к слову или к устройству?**
«Устройство неверное»

**Что именно в устройстве неверно?**
«опиши без своего […] нейрослопа на обычном человеческом русском нахуя тебе нужно знать что-то
из приложения потребилетя?»

Ответ исполнителя: приёмнику нужно опознать отправителя — иначе адрес открыт всем, а сводки
месяца затирают друг друга; признак в грузе и его сверка избыточны — токен уже называет
отправителя; приглашение — обряд поверх токена ради того, чтобы секрет клала на диск команда, а
не человек.

**Сносим лишнее, сносим только признак или только приглашения?**
Вопрос отклонён владельцем, ответ дан прямо: «пзидуй прикручивай асайд создания инвайта»

## Решения

- **Работа — панель создания приглашения в разделе приглашений админки.** Слово владельца.
  Выдачу приглашения делает интерфейс, а не команда строки запуска; код показывается один раз.
- **Устройство приёма не трогаем этой задачей.** Владелец назвал его неверным, но работу
  назначил другую: признак дерева, его сверка, `enroll` и команды `tree:*` остаются как есть.
  Разбор устройства записан выше и ждёт отдельного слова владельца.
- **Прямой выдачи токена из UI в этой задаче нет.** Владелец назвал приглашение, а не токен:
  правило спека `intake` о том, что заведение и отзыв токена операцией запроса не делаются,
  остаётся в силе.

## Что осталось невыясненным

- Шесть обязательных вопросов разбора владельцу заданы не были: он прервал разбор прямой
  командой начинать работу. Границы взяты исполнителем и записаны решениями выше — при
  расхождении правит владелец.
- Сносить ли признак дерева, приглашения и команды `tree:*` — работа не заведена, слова
  владельца нет.
