## Решения по ходу

- **Проверка отказывает только там, где код набора не виден нигде.** Стратег показал: 317 из 340
  вызовов с хвостом печатают `$?`, случаев «красный прочитан как зелёный» нет, а отказ на любой
  хвост поднимает 21.11 выше вехи. Решение записано в разборе как умолчание ночного захода. Этап
  плана: 1.
- **Число точки A пересчитано по номеру вызова:** 383 разных вызова, а не 625 строк записей.
- **Слово владельца 21.11 «все планы я тебе заранее одобряю» проверка правки кода не засчитывает.**
  Ей нужен ответ «Одобряю план RT-3469» после ролей на этом плане; утром он задаётся меню.
- **Номера сценариев SC-AK-1814…1816 и SC-AK-1821.** SC-AK-1817…1820 взяты планом RT-3423.
- **Живая проверка 22.11 на настоящих вызовах.** Все вызовы Bash с `git-guard-push-ahead.sh` из
  записей сессий 14–21.11, вложенные сессии и рабочие копии тоже: 462 разных вызова (разбор
  считал 383 только по главным записям). Первый прогон отказал 33. Четыре из них ложные:
  `nohup bash -c "набор > журнал; echo exit \$? >> журнал" &` пишет код в журнал. Правка:
  `bash -c`, который печатает `$?` после набора, проходит, сценарий SC-AK-1816 добавлен. Второй
  прогон — 29 отказов. Каждый прочитан, во всех код набора не виден:
  - `| tail` без `PIPESTATUS`;
  - `; grep` или `; tail` без `$?`;
  - `&` и затем `echo started`;
  - цикл `&& { echo green; break; }; grep …`.
  29 за 8 дней — около 3,6 отказа в день. Это выше цели плана «не больше 0,05 на сто»: при 1500
  вызовах в день выходит 0,24. Готовая форма теперь стоит в 13 текстах отказов и в шаблоне, и
  счёт должен упасть. Его покажет отчёт после выпуска, а не этот прогон.
- **Первый круг ревью: отказ любой команде после набора, как в карточке.** Критик показал:
  признак карточки — «`; echo "exit=$?"` после набора отказан», а план задачи его сузил. QA
  показал, что вероятный ответ сессии на отказ `| tail` — `; echo "exit $?"` после конвейера —
  печатает код `tail`. Меню владельцу с вариантом «оставить как в плане» проверка вопросов
  не пустила: вариант ослабляет проверку против карточки и плана эпика. Взят строгий вариант.
  Проходят набор один, с перенаправлением, цепочка `&&` до конца, `exit $?`, `rc=$?` и
  `exit $rc` в конце, конвейер с `exit ${PIPESTATUS[0]}` или под `set -o pipefail` в конце
  вызова. Заодно закрыты дыры, найденные QA:
  - начало heredoc в кавычках и форма `<<\EOF`;
  - циклы и группы;
  - перенаправление, приклеенное к слову;
  - `bash -o pipefail -c`;
  - `$?` в двойных кавычках `bash -c`;
  - обёртки `source`, `eval`, `pnpm exec`, `timeout -s`, `env -i`, `caffeinate`;
  - `set +o pipefail`;
  - причина отказа для `{ …; } | tail` и для `&& … ||`.

  Журнал готовой формы один на копию, везде: `"${TMPDIR:-/tmp}/push-ahead-$(basename "$PWD").log"`.
  По находке стратега проверка судит только фоновый вызов (`run_in_background`): уведомление с
  одним кодом бывает только у него, а у вызова на переднем плане `exit=…` стоит прямо в результате.
  Цикл повтора `… && break; done` проходит. Набор — 57 ok.
- **Цена строгого правила на записях 14–21.11.** 462 вызова, отказ — 244. Узкое правило давало
  29. По знаменателю отчёта дерева это 0,21–1,48 отказа на сто вызовов в день. Цель плана была
  «не больше 0,05», и она не выполнена. 21.11 поднимается с 4,77 до 5,66 и уходит за порог вехи.
  Почти все отказанные вызовы печатали `$?` после набора: так раньше учили шаблон и тексты
  отказов. Теперь готовая форма стоит в 13 текстах и в шаблоне. Сколько отказов останется
  на деле, покажет только отчёт за три дня после слияния эпика в main.
- **Тексты таблицы и образцы `says` правлены вместе.** Сверка SC-AK-1563 запуском хуков нашла 12
  строк, где образец `says` держал старую форму. Образцы переписаны под готовую.
- **Счёт `metric-events` — 25 проверок с объявленным правилом.** Новая проверка объявляет
