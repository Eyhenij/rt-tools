- Правило `task-flow`: код правится только после плана, ступени помечаются в прогрессе.
- Правило `spec-driven`: у каждого нового сценария свой номер и тест с тем же номером в названии.

## Questions and answers

Вопросов владельцу нет: каждая запись называет и место, и готовую правку, а порядок работы задан эпиком.

## Decisions

- **Четыре правки идут четырьмя этапами в одной ветке** — все четыре в одном пакете и друг от друга не зависят; так задаёт план эпика. Rejected: четыре ветки — по ветке на запись раздувает цепочку PR без выгоды.
- **Груз наблюдений делится по дню в `shipmentsOf`, а не в отправителе** — приём замещает день целиком, поэтому у каждого дня своя отправка; отказ одного не останавливает остальные. Rejected: делить по числу строк — приём так не считает.
- **Чтение карточки при заведении идёт прямым запросом `projectItems` по задаче, окно ожидания растёт паузой до ~30 секунд** — прямой запрос по замеру в записи 0,8 с против 2,9 с на весь список. Rejected: больше повторов старого чтения — чтение остаётся тяжёлым.
- **Запрос выкатки идёт без фильтра по статусу, двадцать последних прогонов** — готовый текст из записи.

## What is left unclear

- Сколько секунд ждать в окне заведения: запись называет «около 30», берётся 30 суммарно (1, 2, 4, 8, 15 секунд). Не блокирует: число лежит в одной константе.
