# Grill

Работа начата по слову владельца в эпике RT-3641; груза из приёмника нет.

## The owner request

> Выпуск `@rt-tools/ui-kit-v2` 0.52.0 заметно тяжелее 0.51.0, и два потребителя вышли за бюджет стартового пакета. Задача: найти, что утяжелило части кита, и вернуть вес без потери возможностей 0.52.0.

> «запускай task flow» — после плана, где пресеты и темы подключаются по требованию, а токены режутся на файлы. Затем: «Влил, дальше» после RT-3644.

## What the tree already has

- Диалог подтверждения пункта меню — `RtMenuConfirmDialogComponent` в `projects/ui-kit-v2/src/lib/components/menu/rt-menu-confirm-dialog.component.{ts,html,scss}`. Его статически импортирует только `rt-menu-item.component.ts`, где конструктор подписывается на запросы подтверждения и открывает диалог через `RtDialogService.open(...)` в `mergeMap`.
- Публичная точка `menu` (`index.ts`) класс диалога не экспортирует: ломающей правки здесь нет, в отличие от RT-3645. Класс упомянут ещё в своём тесте и в обёртке витрины (`stories/component/test-menu-confirm-dialog-matrix.component.ts`), оба внутри пакета.
- Сторож веса (RT-3642): часть `menu` — 39659 байт, набор частей — 331452 байт (порог до слияния RT-3645).
- Диалог тянет `RtDialogComponent`, кнопку, шаблон и стили. `dialog` входит в набор как отдельная точка, поэтому от диалога подтверждения со старта уходит только то, что лежит в самой части `menu`.
- Подтверждения открываются редко: пункт с `confirmMessage`, не ссылка.

## What the rules already say

- `rt-tools-styling`: вид кита не меняется без согласия владельца; задача вида не меняет.
- Описания меню в `docs/specs/ui-kit-v2/` нет: правило подтверждения записано только в коде и в `Overview.mdx` меню.
- Цель по плану эпика: минус 3–5 КБ на старте.

## Questions and answers

Владелец подтвердил эпик и порядок словами «запускай task flow» и «Влил, дальше»; отдельных вопросов по задаче не задавалось: способ определён кодом и измерением.

## Decisions

- **Диалог грузится ленивым `import()` в момент подтверждения, подписка остаётся в конструкторе.** Внутри `mergeMap` загрузка кода стоит перед `open`; `mergeMap` остаётся, поведение при двух подтверждениях подряд не меняется. Повторное подтверждение берёт готовый код сразу.
- **Сбой загрузки куска не оставляет меню в состоянии «жду ответа».** Без перехвата ошибка убила бы весь поток подтверждений пункта. Перехват стоит внутри `mergeMap`: ошибка идёт обработчику ошибок приложения, меню получает `#announceConfirm(false)`, поток живёт и следующее нажатие пробует снова. Так же закрыт сбой в листе popover.
- **Известное ограничение:** меню, закрытое за время загрузки куска, не отменяет открытие диалога; окно между щелчком и диалогом стало длиннее, но случай редкий.
- **Публичный контракт не меняется.** Класс диалога из точки не экспортировался. Номер выпуска задача не меняет.
- **Ожидание: 3–5 КБ по цели эпика, нижняя граница плана 2000 байт, цифру даёт сторож.** Оценка по сборке esbuild 4,5–5,2 КБ, по размеру исходников 1–2 КБ; gzip выигрывает около 1,2 КБ. Итог называет разницу честно, как в RT-3645.
- **Вид и поведение диалога не меняются.** Меняется только момент загрузки его кода: первое подтверждение ждёт один запрос файла.

## What is left unclear

- Первая задержка на медленной сети при первом подтверждении; в сборке потребителя не мерили, называется в итоге задачи.
- Сколько байт уйдёт со старта: определяется измерением сторожа.
