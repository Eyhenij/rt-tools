## Что считается сделанным

- Команда заведения после четвёртого шага спрашивает очередь работ о заведённой задаче и печатает
  ответ: присутствие на доске, колонку, исполнителя.
- Задача, не попавшая в очередь, кончает команду ненулевым кодом, а не строкой успеха.
- Правило поставки называет ответ очереди тем, чем подтверждается заведение, — во всех трёх
  редакциях по хостингам.
- Паттерн отчёта называет сверку сразу за вызовом команды и отдельно — проверку серии заведений
  сверкой очереди целиком; тоже во всех трёх редакциях.
- Закон о ведении работы называет отрицание, полученное одним источником, не отрицанием.
- Новое поведение команды покрыто сценариями и стоит в спеке домена с привязкой к коду.
- Дерево разложено выпущенной редакцией, и `agent-kit sync --check` сходится.

## Этапы

### 1. Договорённость о продукте

- **Что делается:** спек фичи и сценарии в `docs/specs/agent-kit/proposed/task-created-verified/`
  — что команда печатает, чем кончается при отсутствии задачи в очереди, что говорят закон,
  правило и паттерн.
- **Признак готовности:** сценарии несут номера общей нумерации домена и помечены «Не покрыто».
- **Чем проверяется:** `pnpm run check:specs` не заводит новых расхождений сверх накопленных.

### 2. Статья закона

- **Что делается:** в `assets/laws/work-conduct.md` следом за статьёй об утверждении о дереве
  встаёт статья об отрицании, полученном одним источником.
- **Признак готовности:** статья говорит, что ответ «не найдено», отказ в доступе и пустой список
  говорят о правах спрашивающего, а не о предмете.
- **Чем проверяется:** `node tools/check-file-size.mjs` на файле закона, чтение целиком.

### 3. Статья правила поставки

- **Что делается:** во все три редакции `assets/rules/git-workflow.*.md` — статья о том, что
  заведённая задача подтверждается ответом очереди работ, а не выводом команды заведения.
- **Признак готовности:** статья стоит рядом со статьёй о явном добавлении на борду в каждой из
  трёх редакций, формулировка одна.
- **Чем проверяется:** `projects/agent-kit/tests/texts.test.sh`, сверка трёх файлов грепом.

### 4. Шаг паттерна отчёта

- **Что делается:** во все три редакции `assets/patterns/git-workflow-commit.*.md` — сверка задачи
  по номеру сразу за вызовом команды и проверка серии заведений сверкой очереди целиком.
- **Признак готовности:** шаг стоит между заведением задачи и заведением ветки, с готовым вызовом.
- **Чем проверяется:** тот же набор сценариев текстов.

### 5. Команда заведения печатает ответ очереди

- **Что делается:** `assets/checks/task-new.github.mjs` после четвёртого шага спрашивает борду о
  заведённой задаче и печатает присутствие, колонку и исполнителя; отсутствие — отдельная строка
  и ненулевой код.
- **Признак готовности:** оба исхода различимы по выводу и по коду возврата.
- **Чем проверяется:** сценарии в `projects/agent-kit/tests/checks.test.sh`, прогон
  `projects/agent-kit/tests/run.sh`.

### 6. Раскладка, привязки и журнал

- **Что делается:** привязки сценариев в `docs/specs/agent-kit/implementation.md`, раскладка
  дерева `pnpm run agent-kit:sync`, запись в `## [Unreleased]` журнала пакета.
- **Признак готовности:** `pnpm run agent-kit:check` сходится, разложенные копии несут новые
  статьи, журнал называет правку.
- **Чем проверяется:** `pnpm run agent-kit:check`, `pnpm run check:docs`, `pnpm exec nx affected -t lint typecheck test build`.

## Чего эта работа не делает

- Не чинит сокрытие машинной учётной записи хостингом: это ограничение снаружи, и работа с ним
  описана компаньоном правила задачей #559.
- Не трогает сверку очереди работ `check-board`: её слепые пятна — задача #540.
- Не заводит статью о пустом выводе команды, к которой предложение #557 привязывалось местом:
  она приедет задачей #551, и новая статья встаёт рядом с той, что уже есть.
