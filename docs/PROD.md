# Прод приёмника

Где стоит приёмник, из чего он поднят, как до него доходит запрос и что делать, когда он молчит.
Правится тем же движением, что и `docker-compose.prod.yml`: расхождение здесь копится молча, а
читают этот текст как действующий.

## Узел

| Что             | Значение                                           |
| --------------- | -------------------------------------------------- |
| где             | самый малый узел DigitalOcean, Сингапур            |
| система         | Ubuntu 24.04 LTS, x86_64                           |
| чем поднято     | Docker и Compose, поставленные пакетами системы    |
| учётная запись  | `deploy` — она в группе докера, ей же идёт выкатка |
| каталог выкатки | `/opt/message-bus`                                 |
| имя             | `message-bus.dev` — зона живёт у DigitalOcean      |
| имя чата        | `chat.message-bus.dev` — тот же узел и та же зона  |

Что лежит в каталоге выкатки: состав прода, конфиг дороги, сценарий чистки образов, сценарий
дампа и окружение прода. Кода там нет вовсе — он внутри образов.

## Путь запроса

```
дерево или браузер  →  дорога (Caddy)  →  приёмник  →  хранилище
   HTTPS по имени       80 и 443           3000        5432, наружу закрыт
```

Наружу открыты только два порта дороги. Приёмник и хранилище портов не публикуют: попасть в
приёмник можно лишь через дорогу, в хранилище — только с самого узла.

Дорога делит запросы по адресу: `/api/*` уходит приёмнику, всё остальное отдаётся статикой
админки, лежащей в том же образе. Адрес раздела админки — не файл: на такой запрос отдаётся
страница приложения, а не отказ.

Сертификат выписывает и продлевает сама дорога. Отдельного тайминга и своего клиента ACME на
узле нет. Состояние выдачи лежит на именованном томе: без него каждая выкатка просила бы новый
сертификат и упёрлась бы в недельный предел выдач.

## Чат

Чат живёт внутри приёмника: своих контейнеров у него нет ни одного. Операции посетителя объявлены
теми же контроллерами, раздел оператора — той же админкой, а будильник переписок держит таймер
внутри приёмника — расписания на узле не заведено.

По имени чата дорога отдаёт два рода запросов: `/api/*` уходит приёмнику, `/widget.js` — файлом
из того же каталога, где лежит статика админки. Остального по этому имени нет: админка живёт на
главном имени, и вход человека пользуется кукой того имени.

Страница чужого приложения берёт виджет по адресу `https://chat.message-bus.dev/widget.js` и
называет ключ площадки тегом. Браузер такой страницы спрашивает у сервиса позволение обращаться,
и даёт его приёмник — по списку адресов площадки, лежащему на её записи. Дорога о площадках не
знает ничего, и её позволение было бы одно на всех.

Что нужно сделать руками до первой выкатки чата: завести в зоне запись `chat` на адрес узла.
Сертификат на неё дорога выпишет сама, как и на главное имя, но имени, которого нет в зоне, она
сертификата не получит — и выдача упрётся в предел попыток.

```bash
dig +short chat.message-bus.dev                 # должен ответить адресом узла
curl -sI https://chat.message-bus.dev/widget.js # 200 и тип JavaScript
```

## Состав прода

Четыре контейнера, и порядок между ними значим:

| Контейнер | Что делает                                              | Когда поднимается                  |
| --------- | ------------------------------------------------------- | ---------------------------------- |
| `db`      | хранилище на именованном томе                           | первым, до готовности пробы        |
| `migrate` | накат миграций и выход                                  | после готовности хранилища, разово |
| `api`     | приёмник                                                | только после удачного наката       |
| `web`     | дорога: имя, сертификат, статика админки, проксирование | после того, как приёмник запущен   |

Метка образов — sha коммита, а не «последний»: подвижная метка отстаёт от главной ветки, и узел
молча остался бы на прежней версии, продолжая отвечать.

## Команды приёмника

Заведение дерева, выдача токена, список деревьев и учётные записи зовутся одной командой —
доводы уходят приёмнику как есть:

```bash
pnpm run prod:api tree:list
pnpm run prod:api tree:add 'Имя дерева' a1b2c3d4e5f6
```

Признак дерева — первые двенадцать знаков хеша от адреса его удалённого репозитория; считается
он в том дереве, которое заводится, а не здесь. Токен печатается один раз, в ответ на
`tree:add`; потерянный не показывается больше никогда — вместо него выдаётся новый командой
`tree:token`, отзывающей прежний.

Перечень команд печатает сам приёмник на незнакомом доводе: `pnpm run prod:api help`. Без
доводов команда не зовётся вовсе — пустой довод у точки входа образа означает не перечень, а
вторую поднятую службу рядом с работающей.

## Выкатка

Идёт рукой: рабочий поток `Deploy` запускается кнопкой, из главной ветки. Запуск с ветки доходит
до сборок образов и там кончается — так проверяется правка самого конвейера, не трогая узел.

Что делает выкатка по шагам: собирает оба образа на раннере машины под платформу узла, кладёт их
в реестр под sha коммита, копирует на узел состав прода и сценарии, просит узел вытянуть образы
того же sha и поднять состав, спрашивает пробу живости снаружи по имени и после её ответа чистит
старые образы, оставляя три последних sha.

Секреты выкатки — в настройках репозитория: ключ доступа к узлу, его адрес, учётная запись и
адрес приёмника для пробы. Пароль хранилища живёт только на узле, в `.env.prod`, и выкаткой не
трогается: она правится чаще, чем пароль.

## Дамп

```bash
ssh message-bus 'bash /opt/message-bus/dump.sh save'
ssh message-bus 'bash /opt/message-bus/dump.sh load /opt/message-bus/dumps/<файл>'
```

Дамп несёт хранилище целиком: деревья, токены, учётные записи, записи месяца, предложения,
разборы, а с чатом — площадки, посетителей, переписки, реплики и записи вызовов наружу. Отбора в
дампе нет вовсе, и чату ничего своего здесь не нужно. Загрузка идёт поверх работающего хранилища и перезапускает приёмник — клиент держит
соединения, снятые загрузкой.

Копии дампа лежат на самом узле, в `/opt/message-bus/dumps`. За пределы узла они не уезжают: это
отдельная работа, и она не сделана.

Выгрузка идёт по расписанию раз в сутки, ночью по времени узла; строка задания лежит в
`deploy/dump.crontab`, и в расписание пользователя узла её ставит выкатка. На узле живут семь
последних дампов, старше снимаются после удачной выгрузки; журнал — `/opt/message-bus/dump.log`.
Выкатка каталог дампов и журнал не трогает. Что расписание стоит, спрашивают у узла, а не у
дерева:

```bash
ssh message-bus 'crontab -l | grep dump.sh; ls -la /opt/message-bus/dumps; tail -3 /opt/message-bus/dump.log'
```

Проверять загрузку боевым хранилищем нельзя: второго узла под пробу нет, а откатываться пришлось
бы тем же путём, который и проверяют. Проба идёт на одноразовой базе рядом — тот же образ базы,
то же окружение прода, и боевое хранилище не трогается вовсе:

```bash
ssh message-bus 'bash /opt/message-bus/dump.sh probe'            # снимает свежий дамп и проверяет его
ssh message-bus 'bash /opt/message-bus/dump.sh probe /opt/message-bus/dumps/<файл>'
```

Проба загружает дамп тем же путём, что и `load`, и судит его отпечатками, а не взглядом: по
каждой таблице считаются строки и сумма всех строк в обеих базах. Сошлось — код 0 и свод по
таблицам; разошлось — код 1 и строка на каждую таблицу, где боевая база и дамп отличаются.
Контейнер пробы сносится вместе с томом и при отказе тоже. Проба со старым файлом расходится
законно, если с тех пор приехал груз: сверять старый дамп имеет смысл только с его же временем.

## Вход: общий Keycloak

Админка и приёмник входят через общий Keycloak, область `rt`. Keycloak стоит на своём узле, а не
рядом с приёмником: через него входят все продукты, и выкатка или сбой одного продукта не должны
уносить вход остальных.

| Что             | Значение                                                                  |
| --------------- | ------------------------------------------------------------------------- |
| где             | отдельный узел DigitalOcean, Сингапур, 2 ГБ                               |
| ssh             | `ssh auth`, учётная запись `deploy`                                       |
| каталог выкатки | `/opt/auth`                                                               |
| имя области     | `auth.message-bus.dev`, выдавший `https://auth.message-bus.dev/realms/rt` |
| состав          | `deploy/auth/prod/docker-compose.prod.yml`: Keycloak, Postgres, Caddy     |
| выкатка         | workflow «Deploy Auth», запуск рукой из главной ветки                     |
| дамп            | ночью, `DUMP_NAME=auth bash /opt/auth/dump.sh save`                       |

Область `rt` собирает `node tools/auth-realm-prod.mjs` из файла стенда: клиента примера в ней нет,
адрес админки — прод, а секреты и почта — подстановки `$(env:…)`. Значения лежат только в
`/opt/auth/.env.prod`: `POSTGRES_*`, `KC_ADMIN_USER` и `KC_ADMIN_PASSWORD`, `AUTH_HOSTS` — имена
входа через запятую, `RT_USER_IMPORT_SECRET`, `RT_CATALOG_SYNC_SECRET`, `RT_CARGO_TOOLS_SECRET`,
`RT_VERIFY_EMAIL`, `RT_SMTP_*`, `RT_GOOGLE_*`.

Другие продукты держат файлы своих областей у себя и кладут их в `/opt/auth/realm/`. Выкатка
отсюда перезаписывает только `realm/rt.json` и чужие файлы не трогает. Имя входа продукта
дописывается в `AUTH_HOSTS`.

Приёмник получает вход из своего состава: `AUTH_ISSUER`, `AUTH_CLIENT_ID=rt-message-bus-admin`,
`AUTH_SERVICE_CLIENTS=rt-cargo-tools`. В `.env.prod` приёмника дописывается `AUTH_SYNC_SECRET` —
то же значение, что `RT_CATALOG_SYNC_SECRET` у Keycloak. Без него приёмник не поднимается.

Порядок выкатки эпика входа:

1. «Deploy Auth» — Keycloak отвечает по `https://auth.message-bus.dev/realms/rt`.
2. Выгрузка и импорт людей — раздел ниже, шаги 1–3.
3. `AUTH_SYNC_SECRET` в `.env.prod` приёмника.
4. «Deploy» приёмника.
5. Ключи операторов чата — раздел ниже, шаг 5.

## Перенос людей в Keycloak

Выкатка эпика входа через Keycloak удаляет из хранилища таблицы людей. Поэтому люди уходят в
Keycloak до неё, в таком порядке:

1. **Адреса.** В `~/.config/rt-bus-transfer/addresses.json` лежат пары «имя записи — адрес».
   Адрес станет логином в Keycloak.
2. **Выгрузка, до выкатки.** `node tools/bus-people-transfer.mjs export` читает людей прода одним
   запросом на чтение. Он пишет файл для импорта и карту ключей рядом с адресами. Запись без
   адреса останавливает выгрузку. Отключённые записи и служебная запись разбора груза остаются,
   отчёт их называет.
3. **Импорт.** `rt-auth-import --url <keycloak> --realm <область> --client-id <клиент импорта>
--file ~/.config/rt-bus-transfer/people.json` заводит людей с ролями клиента шины. Пароли не
   переносятся: при первом входе человек задаёт новый.
4. **Выкатка эпика.**
5. **Операторы чата.** `node tools/bus-people-transfer.mjs rekey --url <keycloak> --realm <область>
--client-id <клиент импорта>` печатает запрос, который даёт операторам ключи людей в Keycloak.
   С `--apply` он выполняется на проде одной транзакцией. Секрет клиента импорта берётся из
   `RT_AUTH_IMPORT_CLIENT_SECRET`.

## Когда приёмник молчит

Порядок разбора — от дешёвого к дорогому:

1. **Имя разрешается?** `dig +short message-bus.dev` — должен ответить адресом узла.
2. **Узел жив?** `ssh message-bus 'uptime'`.
3. **Что с контейнерами?** `ssh message-bus 'cd /opt/message-bus && docker compose -f docker-compose.prod.yml --env-file .env.prod ps'` — здесь видно, какой из четырёх упал.
4. **Что говорит приёмник?** `... logs --tail 100 api`. Строки машинные: отказ приёма стоит под именем `intake.failed`, всякий другой — под `request.failed`, и у поломки в поле причины лежат класс ошибки, её текст, код клиента хранилища и ответ драйвера. Отбирать их удобно по имени: `... logs api | grep request.failed`.
5. **Место на диске.** `ssh message-bus 'df -h /; docker system df'` — узлу 24 ГБ, и хранилище, упёршееся в полный диск, гаснет чужим лицом: наружу это выглядит молчащим приёмником.
6. **Сертификат.** `... logs --tail 100 web` — предел выдач Let's Encrypt виден только здесь.

Откат: поднять прежний sha руками.

```bash
ssh message-bus 'cd /opt/message-bus && IMAGE_TAG=<прежний sha> \
    docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --no-build'
```

Три последних sha на узле держит чистка — глубже отката нет.
