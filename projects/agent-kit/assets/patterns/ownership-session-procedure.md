# Процедура, которой нужна сущность захода

Паттерн правила `ownership-session`. Что при этом должно быть верно — закон
`docs/constitution/application/ownership.md`.

## Когда брать

- Процедура работает с записями владеющей сущности и должна знать, в какой она работает.
- Процедура читает идентификатор сущности из полей запроса — так больше не делают.
- Пишется тест процедуры, которая сущность захода читает.

## Объявление и чтение

Две строки пишутся вместе: декоратор на классе и чтение из контекста в теле. Перехватчик читает
сущность только для объявивших, поэтому чтение без декоратора отвечает внутренней ошибкой — и
отвечает на первом вызове, а не на сборке.

```ts
@Injectable()
@ConnectProcedure()
@RequiresPermission('settings:view')
@RequiresOwner()
export class GetSettingsProcedure implements IConnectProcedure<typeof SettingsContract.method.getSettings> {
    public async handle(
        _request: GetSettingsRequest,
        context: HandlerContext
    ): Promise<MessageInitShape<typeof GetSettingsResponseSchema>> {
        const settings: IOwnerSettings = await this.#settings.byOwner(ownerOf(context));
        …
    }
}
```

Запрос при этом не читается вовсе — отсюда `_request`. Поля сущности в контракте нет: номер и
имя помечены занятыми, а присланный ключ отбивается разбором запроса. Заводить его заново
нельзя: сущность в запросе называет только тот, кто работает поверх всех сразу.

Декоратор потребности стоит рядом с объявлением доступа, а не вместо него: объявлений доступа у
процедуры по-прежнему ровно одно, и без него приложение не поднимется.

## Идентификатор, названный в теле запроса

Некоторые запросы несут сущность не отдельным полем, а внутри черновика. Расхождение с
сущностью захода отбивается, а не выправляется молча:

```ts
const sessionOwnerId: string = ownerOf(context);
if (draft.id && draft.id !== sessionOwnerId) {
    throw new ConnectError('owner does not match the session owner', Code.InvalidArgument);
}
```

Пустой идентификатор в черновике законен: он приходит пустым, когда админка сохраняет то, чего
ещё не загружала.

## Контекст в тесте

Двойника перехватчика заводить не надо — в контекст кладётся готовое значение:

```ts
function context(ownerId: string): HandlerContext {
    const values: ContextValues = createContextValues();
    values.set(kSessionOwner, ownerId);

    return { values } as unknown as HandlerContext;
}
```

Тест на то, что присланный идентификатор не читается, пишется отдельным случаем: запрос несёт
чужую сущность, а спросили у хранилища свою.

```ts
it('SC-OWN-54 — читает сущность захода и присланный идентификатор не смотрит', async () => {
    const request: GetSettingsRequest = create(GetSettingsRequestSchema, { ownerId: FOREIGN_OWNER });

    await procedure.handle(request, context(SESSION_OWNER));

    expect(asked).toEqual([SESSION_OWNER]);
});
```

## Частые промахи

- Декоратор забыт, а чтение в теле стоит. Сборка и линт молчат, отказ приходит на первом вызове.
  Ловится тестом процедуры, а не проверками дерева.
- Декоратор поставлен вместо объявления доступа. Приложение не поднимется: у процедуры обязано
  быть ровно одно объявление доступа, а потребность в сущности к ним не относится.
- Сущность прочитана из запроса «на всякий случай, если контекст пуст». Пустой контекст здесь
  означает забытое объявление, и подстановка прячет его до самого прода.
- Процедура читает сущность захода у гостя. Вошедшего у гостевых процедур нет, и сущности в
  контексте у них тоже нет: они берут её у записи, с которой пришли, — у страницы, у разговора
  по токену, — а когда записи нет вовсе, у единственной сущности хранилища. Второй в хранилище
  они отвечают отказом по состоянию.
- Отказ на снятую принадлежность подан как отказ в доступе. Транспорт админки уводит на вход
  только по коду неаутентифицированного, а на второй код человек остаётся на закрытом разделе.
