# Вливание главной ветки в ветку задачи

Паттерн правила `git-workflow`. Что при этом должно быть верно — закон `{{lawsDir}}/delivery.md`.

## Когда брать

- PR отмечен конфликтующим, и его надо вернуть к сливаемому состоянию.
- Главная ветка ушла вперёд, и ветку задачи надо подтянуть до проверок.
- Коммит переносится отдельным выбором.

## Порядок

```bash
git fetch origin
git merge origin/<главная ветка> --no-edit
git diff --name-only --diff-filter=U     # что встало конфликтом
```

Список конфликтов читается целиком до первого разрешения: род файла решает приём, и разные
файлы одного слияния разрешаются по-разному.

| Что встало конфликтом | Как разрешается                                                                |
| --------------------- | ------------------------------------------------------------------------------ |
| код                   | ловушка правила `git-workflow` про сторону-удаление; после — проверка повторов |
| спек домена           | сохранением обеих сторон — правило `spec-driven`; после — проверка спеков      |
| накопительный список  | признаком отбора — паттерн `doc-style-sweep`                                   |

## Что дописала ветка, видно только от точки расхождения

Конфликтный маркер показывает место, а не правку: сторона ветки в нём — её допись вместе со
всем, что лежало в файле до неё.

```bash
git diff "$(git merge-base origin/<главная ветка> HEAD)" HEAD -- <файл>
```

## Дописанное веткой сверяется с очередью работ, а не переносится по умолчанию

Раздел, который ветка дописала в накопительный список, к моменту слияния обычно уже стоит
задачей: ветка живёт неделями, а замеченный по ходу дефект заводится задачей сразу. Перенести
его второй раз — завести вторую запись об одной работе.

Когда задача несёт то же содержание, сторона ветки не переносится:

```bash
git checkout --theirs <файл> && git add <файл>
```

При слиянии `--theirs` — влитая главная ветка, а `--ours` — ветка задачи; при перебазировании
стороны меняются местами. Взятая не та сторона стирает работу молча.

## Проверки после разрешения

Конфликт в текстах кода не задевает, и зелёная сборка про него ничего не говорит:

```bash
grep -rn '^<<<<<<< \|^>>>>>>> ' --exclude-dir=node_modules --exclude-dir=.git .
```

Следом гоняются проверки текстов, раскладки, повторов и очереди работ, а если конфликт задел
хуки — их сценарии. Коммит слияния подписывается так же, как любой другой, — паттерн
`git-workflow-commit`. После пуша состояние читается у самого PR, а не по своему дереву.

## Тело открытого PR перечитывается после слияния

Отчёт описывал дерево на день, когда его написали. Вливание главной ветки меняет то, о чём он
утверждает: тело говорит про записи, которые главная ветка к тому времени уже разобрала.

## Частые промахи

- «Сохранить обе стороны» применено ко всем файлам одинаково: в спеке это верно, в коде и в
  накопительном списке — нет.
- Сторона ветки перенесена без сверки с очередью работ: одна работа стала двумя записями.
- После разрешения прогнана сборка, а проверки текстов — нет: конфликта в них сборке не видно.
- Тело PR оставлено прежним: ревьювер читает утверждение о дереве, которого больше нет.
