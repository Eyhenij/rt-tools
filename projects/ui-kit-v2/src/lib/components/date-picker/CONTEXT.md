# `rt-date-picker`

```html
<rt-field label="Дата заезда">
    <rt-date-picker type="date" min="2026-01-01" max="2026-12-31" [formControl]="checkIn" />
</rt-field>
```

Свои входы поверх общих из [`RtFormControlBase`](../form-control/CONTEXT.md):

| вход          | тип                                    | умолчание |
| ------------- | -------------------------------------- | --------- |
| `type`        | `'date' \| 'time' \| 'datetime-local'` | `'date'`  |
| `min` / `max` | `string \| null` (ISO)                 | `null`    |

Значение — **строка ISO**, ровно та, что отдаёт нативное поле (`2026-03-15`, `09:30`,
`2026-03-15T09:30`).

## Главное, что нужно знать

**Своего календаря кит не везёт — рисует его браузер.** Отсюда всё остальное: раскладка,
формат ввода и клавиатура всегда совпадают с системными, а вид поля на разных платформах
отличается. Если нужен единый календарь во всех браузерах, этот компонент не подойдёт.

**Значение — строка, а не `Date`.** Разбор и часовые пояса остаются на стороне потребителя;
компонент не трогает ни то, ни другое.

## Края

- В плоском режиме чтения (включает [`rt-field`](../field/CONTEXT.md)) значение переписывается
  на язык интерфейса через `Intl.DateTimeFormat`: `2026-03-15` → `15 мар. 2026 г.` под `ru`.
- Нераспознанная строка в этом режиме показывается **как есть**, а не исчезает: значение может
  прийти из формы, минуя нативное поле.
- Пустое значение рисуется прочерком.
- `min`/`max` уезжают на нативное поле; проверку выхода за границы делает браузер, отдельного
  валидатора здесь нет.

## Рядом

- [`rt-input`](../input/CONTEXT.md) с `type="time"` — когда нужно только время без обёртки.
- [`rt-calendar`](../calendar/CONTEXT.md) — календарь-витрина, а не поле ввода.
- Проверки: [`rt-date-picker.component.spec.ts`](./rt-date-picker.component.spec.ts).
