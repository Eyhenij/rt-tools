## Возраст кэша места не гарантирует

Раздел этого дерева: раннер живёт на машине владельца, и уборка за прогоном стоит в самом
конвейере.

Порог по возрасту освобождает то, что накопилось вчера, а место кончается от того, что
накопилось сегодня. За один заход кэш вырос на двадцать один гигабайт, и уборка по суткам
освободила девяносто пять мегабайт — следующий прогон встал на нехватке места. Поэтому у кэша
два ограничителя, а не один:

```bash
docker builder prune --force --filter until=24h        # вчерашний кэш ничей
docker builder prune --force --max-used-space 10GB     # предел размера, независимо от возраста
```

Предел стоит в одном месте — шаге «Убрать за прогоном» в `.github/workflows/ci.yml`, — и
пересматривается там же, если сборки станут тяжелее.

Чужое этим не лечится: тринадцать гигабайт держал том постороннего проекта на той же машине, и
снять его прогон не вправе. Единственное, что он может, — вовремя и внятно отказать.

## Нехватку места называет тот шаг, которому её видно

Раздел этого дерева.

Кончившееся место валит не тот шаг, который его съел, а тот, которому оно понадобилось
следующим: база стенда уходит в вечный перезапуск, а красным становится сквозной набор — список
красных экранов у ветки, не тронувшей ни строки кода. По этому лицу прогон перезапускали дважды
и искали причину в правке.

Поэтому стенд спрашивает базу пробой здоровья до самого набора и, не дождавшись, отказывает с её
логом и занятым местом:

```bash
db=$(docker compose ps -q db)                                        # имя собирается из каталога
docker inspect --format '{{.State.Health.Status}}' "$db"             # healthy или ничего
docker logs --tail 20 "$db"                                          # в отказ печатается это
docker system df                                                     # и это
```

Разбор происшествия — запись «2026-08-19-red-run-blamed-on-a-busy-machine» в приёме.
