Собери предложения, пришедшие из деревьев, и скажи, что из них становится правкой пакета.
Отрезок от пользователя: `$ARGUMENTS` (без довода — три дня).

Зовётся **в репозитории самого пакета**, а не в дереве, где он стоит: здесь лежат ресурсы,
которые предстоит править, и видно всех потребителей сразу. В чужом дереве команда бессмысленна
— там есть только своя половина картины.

## 1. Собери, что пришло

```bash
gh issue list --label agent-kit-feedback --state open --limit 100 \
    --json number,title,body,createdAt
```

Помощник хостинга и учётная запись машинной работы у каждого дерева свои — как их звать здесь,
сказано в компаньоне правила `git-workflow`.

Каждая запись заведена командой `agent-kit propose` из дерева, где пакет стоит. В теле — ресурс,
место, повод, готовый текст и сводка наблюдений того дерева. Имени дерева там нет намеренно:
различать их можно только по сводке и по времени.

Своё дерево тоже потребитель — его наблюдения читаются прямо:

```bash
npx agent-kit stats --days <отрезок> --json
```

## 2. Раздели повторившееся и разовое

Это и есть работа сведения; всё остальное — оформление.

- **Пришло об одном ресурсе из двух и более записей** — правка пакета. Разные деревья
  споткнулись об одно и то же место, и чинить его надо там, откуда оно к ним приехало.
- **Пришло однажды и называет то, чего у других нет** — надстройка того дерева, а не пакет.
  Скажи это прямо и назови, куда именно: `overrides/<ресурс>` для текстов, карта гейта и
  профиль — для родов файлов и команд.
- **Пришло однажды, но верно любому дереву** — правка пакета. Числа записей мало: правило,
  которое молчит о важном, молчит у всех, а споткнулся о него пока один.

Ресурс, о котором пришли **противоречащие** предложения, в правку не идёт вовсе: неси оба
владельцу. Слой правил, который говорит два разных, хуже слоя, который молчит.

## 3. Посмотри, что говорят наблюдения

Сводка отвечает на то, чего в предложениях нет:

- **правило, разложенное и не загруженное ни разу** — кандидат на сокращение или на запись в
  карте гейта: правило, которого гейт не требует, никто и не откроет;
- **правило, которое гейт отбивает чаще прочих** — его либо забывают, либо оно требуется не
  там; посмотри род правки в той же сводке;
- **гард, отказывающий чаще прочих** — либо место поставки раз за разом делают не так, либо
  отказ не называет, чем он снимается.

## 4. Принеси правки

По каждой — ресурс, место, готовый текст и число записей, из которых она вышла. Не правь ничего
сам: решение принимает владелец, а работа идёт обычным ходом — задача, ветка, папка задачи.

Заведи задачу на то, что владелец принял:

```bash
npm run task:new -- --title '<что не так>' --slug <короткое-имя> --label enhancement < тело.md
```

Записи, вошедшие в задачу, закрой ссылкой на неё:

```bash
gh issue close <номер> --comment 'Вошло в #<номер задачи>.'
```

## 5. Черновик записи в журнал изменений

Собери его сразу, пока видно, из чего правка выросла: заголовок коммита по формату дерева и
одна фраза о том, что менялось и почему. Журнал изменений при выпуске собирается из заголовков,
и переписывать их задним числом — работа заново.

**Выпуск отсюда не запускается.** Это отдельное решение владельца: слияние отчёта пакета не
публикует. Скажи, что накопилось на выпуск, и остановись.
