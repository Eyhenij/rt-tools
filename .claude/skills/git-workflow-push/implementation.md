# git-workflow-push — what is its own here

The bindings of this tree for the part `git-workflow-push` of the delivery rule, next to its `SKILL.md`.
The names of delivery and the rest of what is its own here are in the companion of
`git-workflow`.

## Where the articles are carried out

The first column is the article verbatim, as it is written in the section «How the law applies
here».

- **On a machine with several runners, any path from the home directory is shared.** — **Not checked by anything.** Neither a guard nor an audit knows how many runners stand on the machine: the host has one list of pipeline steps, and the machine is shared by them only in fact. Held by the article and by per-project names in the pipeline settings
- **A push is sent only by the path the push guard stands on.** — `.claude/hooks/git-guard-push-tests.sh:tool` — the guard judges the shell call and the terminal tab of the session. A terminal or a process started outside the session it does not see; there the set is run by the git hook `.claude/hooks/pre-push.sh` through `.claude/hooks/push-set.sh:rt_push_set_run`, which `.husky/pre-push` wires to git. A push past both — with the hooks skipped — is held by the executor.
- **A review of a foreign branch starts with the gate set run on its tip.** — Not checked by a machine: a review leaves no call the guards can read. The set is `.claude/rt-kit/project.sh:rt_push_checks`, run in a second working copy taken at the tip of the branch. The wording check `tools/check-prose-style.mjs` is not in the set: it stands on an edit and on the cargo send, and in a review it is run over the changed `.md` files by name.
- **Where neither the session's push guard nor the git hook fires, the set is run whole, as read at the minute of the run.** — `.claude/rt-kit/project.sh:rt_push_checks` — the tree has a command that prints the set, `node dist/agent-kit/bin/agent-kit.js doctor`; the set is run whole by the git hook on a push, and by no command apart from it. The lines are also read by `bash -c '. .claude/rt-kit/defaults/project.sh; . .claude/rt-kit/project.sh; rt_push_checks origin/main'`, as the guard reads them: without the first file the function prints only its own 38 lines of 53 and says so on stderr alone.
- **A document goes in the same commit as the edit.** — `.claude/rt-kit/project.sh:rt_docs_pair_for` — the pairs of this tree: a second-kit component's description next to it and the token set description on an edit of the tokens themselves; they are watched by `.claude/hooks/docs-guard.sh`.
- **The commit subject is checked against the format on the spot.** — `commitlint.config.cjs:rules` — the bundle `@commitlint/config-angular` plus the rule `subject-russian`: the description is written in Russian. It is called by a git hook from `.husky/commit-msg`, that is, it judges the hand; a pipeline commit goes past the hook, and the language there is held by the release templates themselves. The cases are `projects/agent-kit/tests/tree-commit-language.test.sh`.
- **Before a push all linters are run, not one.** — `.claude/rt-kit/project.sh:rt_push_checks` — lint, types and specs over the affected, then the styles linter separately: the code linter does not read styles files at all. The set is called by `.claude/hooks/git-guard-push-tests.sh`.
- **The build is in the set on a par with lint and unit tests.** — `.claude/rt-kit/project.sh:rt_push_checks` — the build stands in the same set: a type error in uncovered code turns red nowhere before it.
- **The gate set calls the package default instead of listing it line by line.** — `.claude/rt-kit/project.sh:rt_push_checks` — the profile's own function calls `rt_push_checks_default` and appends the tree's checks to it; what is sifted out is named by name in it too.
- **The final set before a push is read from the state review, not assembled in the head.** — `projects/agent-kit/src/lib/push-gate.ts:pushGateLines` — the section is printed by `node dist/agent-kit/bin/agent-kit.js doctor` after `pnpm run build:agent-kit`. In this tree, under the heading about what the default printed and the set lacks, there stand three lines — those are replacements of the same checks by variants of one's own, not a removal of the guard.
- **The push gate set is never narrower than the pipeline set.** — `tools/check-push-gate.mjs:pipelineSteps` against `pushGate` in `.claude/rt-kit/checks.json`; the check itself stands as a line in `rt_push_checks`. One step of a branch is narrower by the owner's word: the frames go by `node tools/visual-gate.mjs ui-kit-v2 --affected <base>`. The check asks the set with no base and sees the whole line. How many pipeline steps are closed by what it prints on every run — the numbers here are not rewritten.
- **An exclusion reason naming a task is judged on whether that task is alive.** — `tools/check-push-gate.mjs:taskNumbers` — the number is taken out by the task key from `.claude/rt-kit/checks.json`, and the liveness is asked of `tools/board.mjs:taskState`; with no network or no access the poll ends silently.
- **The layout audit stands in the push gate set on a par with lint and the build.** — `.claude/rt-kit/project.sh:rt_push_checks` — the first line of the set is `pnpm run agent-kit:check`: the rules package lies in this same tree, so the audit first rebuilds it and only then reads the built output. The package default prints its own form — `projects/agent-kit/assets/defaults/push.sh:rt_push_checks_default`.
- **After merging the base in, the check set is revised by what the branch now carries.** — Not checked by anything: the guard sees the set but does not know what exactly the merge brought. Held by the checklist before publishing the PR.
- **Guard scenarios set the git settings and the locale themselves, not take them from the machine.** — `projects/agent-kit/tests/git-guards.test.sh:gpgsign` — the author, the mail and the signing are passed by `-c` flags straight into the command rather than inherited from the machine's shared config. The tree's set `tools/tests/run.sh` runs under `LC_ALL=C.UTF-8`, the locale of the push guard.
