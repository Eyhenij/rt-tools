# Честный стенд

Паттерн правила `browser-verification`. Что при этом должно быть верно — закон
`docs/constitution/verifiability.md`.

## Когда брать

- Проверяется то, чего на дев-сервере не видно: разметка от сервера, локали, кэш,
  перенаправления, заголовки, размер бандла.
- Порт отвечает не тем, чего ждали.
- Нужен вход в админку.

## Номера портов объявляет дерево, а не паттерн

Раздел этого дерева: сайта и сервера отрисовки здесь нет, а стендов два — витрина набора
компонентов и стенд сквозного набора со своей засеянной базой.

| Роль                | Порт  | Чем поднимается                    |
| ------------------- | ----- | ---------------------------------- |
| витрина             | 6006  | `pnpm run storybook`               |
| собранная витрина   | 6007  | `pnpm run build-storybook` и отдача |
| приёмник стенда     | 3310  | `pnpm run serve:stand`             |
| админка стенда      | 4310  | тем же вызовом                     |
| приёмник разработки | 3000  | `pnpm run serve:api`               |
| админка разработки  | 4200  | `pnpm run serve:admin`             |
| база разработки     | 55432 | `pnpm run serve:db`                |

Порты стенда сквозного набора переопределяются переменными `E2E_API_PORT` и `E2E_ADMIN_PORT` —
объявлены они в `apps/message-bus-admin-e2e/stand/stand.mjs`. Рабочих портов стенд не занимает:
на нём смотрят то, чего в рабочей базе нет.

Разбор занятого порта, отличение собранного артефакта от дев-сервера и правило «второй экземпляр
не поднимается» верны здесь целиком — ими и пользуются, когда витрина отвечает не тем.

## Сначала — что отвечает на порту

До первого запроса, а не после непонятного ответа:

```bash
lsof -nP -iTCP:$API_PORT -sTCP:LISTEN
```

На порту приёмника регулярно висит собранный артефакт из прошлой сессии
(`node -r dotenv/config dist/apps/api/main.js`): он отвечает 200 старым кодом, а процедуры,
заведённой в ветке, у него нет вовсе. Таких процессов бывает несколько, и снимать надо все —
по PID из `lsof`, каждый: `pkill` по шаблону `nx serve api` не попадает ни в один.

## Прод-сборка сайта

```bash
npx nx build site
PORT=$SITE_STAND_PORT node dist/apps/site/server/server.mjs
```

Это не дев-сервер: гард ловит `nx|ng serve`, пакетные раннеры и статические серверы, а запуск
собранного сервера пропускает.

Поведение, зависящее от хоста — адрес владельца, увод, разный ответ на разных именах, —
проверяется прямо здесь одним запросом с заданным заголовком. Прокси с подменой для этого не
нужен: он добавляет ещё один процесс, чьё поведение придётся отделять от проверяемого.

## Стенд админки

```bash
npx nx build admin --base-href=/
```

Без `--base-href` стенд отдаёт пустую страницу без ошибок в консоли. Стенду, на котором нужен
Angular DevTools, нужна ещё и dev-конфигурация (`--configuration=development`): прод-сборка не
публикует `window.ng`. Выводы о размере бандла и минификации на такой сборке делать нельзя.

Собранное отдаётся прокси дерева с его настоящим конфигом, а не статическим сервером. Причин
две, и обе всплывают в первую минуту: приложение ходит за процедурами на свой же origin, а по
глубокой ссылке статический сервер отвечает `404` — маршрутов одностраничного приложения он не
знает и на его точку входа не откатывается. Гард дев-серверов такой сервер отбивает наравне с
`nx serve`, и это указание на верный ход, а не помеха: готовый вызов — раздел «Стенд под
настоящим nginx» ниже, он и отдаёт собранное, и проксирует процедуры.

Вход делается формой, как у человека. Учётная запись местной базы разработки — не секрет
владельца: её кладёт туда засев того же дерева, а пароль лежит в файле окружения рядом.
Разрешения на неё не спрашивают — спрашивают про боевую запись, а её на местном стенде не
бывает вовсе. Там, где приёмника рядом нет, ответ входа подменяет сам стенд: путь у приложения
остаётся тот же, что у человека.

Токен руками не подписывается и в хранилище браузера руками не кладётся: положенный так, он
проверяет экран, миновав живой путь входа, — то есть отвечает не на тот вопрос. Просьба к
человеку набрать пароль, открыть вкладку или нажать кнопку означает неверно выбранный путь, а
не нехватку прав у исполнителя.

**Спрашивают режим работы, а не ввод.** Ввод в поле пароля отбивает классификатор
автоматического режима: он судит само действие и адресов не различает — стенд на местном порту
выглядит для него боевым сайтом. Ход отсюда один: назвать владельцу отбитое действие, попросить
обычный режим, заполнить форму парой засева самому и вернуться в автоматический режим. Просьба
«войди сам» и «введи пароль» перекладывает на владельца работу агента и выглядит законной ровно
потому, что перед ней стоит настоящее препятствие: отбитое поле, чужое расширение в браузере,
отключившийся профиль. Препятствие остаётся препятствием агента.

Пути, которыми препятствие снимается своими силами, — до всякой просьбы: подстановка значения
инструментом формы по ссылке на элемент, выключение мешающего расширения в профиле браузера,
подъём стенда на другом адресе. Второй драйвер полем пароля не оправдывается: он заполняет то же
поле без классификатора, но обойдённый запрет снимается не с одного поля, а со всех сразу.
Оставленный обычный режим снимает подтверждение и со всех последующих действий захода, поэтому
возврат — часть входа, а не отдельная уборка.

Стенд владельца запасным путём не бывает: он собирает главную ветку и о правке в рабочем дереве
не говорит ничего.

## Стенд API

Собранный артефакт поднимается на свободном порту, а не на порту приёмника: там отвечает приёмник
владельца, и окружение у него не то, которое проверяется.

```bash
npx nx build api
env -u JWT_SECRET NODE_ENV=production API_PORT=$API_STAND_PORT DATABASE_URL=… node dist/apps/api/main.js
```

Переменные окружения задаются в самой команде, по одной на проверяемый случай. Отказ на
старте — такой же результат проверки, как ответ 200: приложение, упавшее в фабрике
провайдера, порт не слушает вовсе, и это видно по `lsof`, а не по тексту в консоли.

Процедура зовётся полным именем, как её объявляет контракт:

```bash
curl -sS -X POST http://localhost:$API_STAND_PORT/<область>.v1.AuthService/GetMe \
    -H 'content-type: application/json' -H "authorization: Bearer $TOKEN" -d '{}'
```

Токен подписывается руками только там, где проверяется сама подпись: доказать, что отладочный
ключ принимается, другого пути не имеет. Во всех остальных случаях токен берётся у живого API
входом — рукописный скрывает расхождение состава притязаний.

## Стенд под настоящим nginx

Раздел этого дерева: прокси здесь нет ни у одного приложения. Админка ходит на приёмник напрямую,
проксируя `/api` на его порт своей настройкой разработки, а витрина — статика без сервера.
Выводов про кэш, перенаправления и заголовки на этих стендах не делают: не на чем.

## Стенд живёт ровно столько, сколько проверка

Стенд поднят под один вывод и после него не нужен. Брошенный не мешает ничему и не подаёт сигнала:
имя у него своё, порт свободный, места он почти не занимает — увидеть его можно только вызовом
списка, а звать его незачем. Разбирать накопленное поэтому приходится человеку, и отличить
брошенный от живого стенда соседнего дерева он по имени не может.

Снос идёт тем же ходом, которым сделан вывод:

```bash
docker rm -f <имя стенда>
```

Имя даётся по номеру задачи — так видно, чей стенд остался, если ход всё-таки оборвался.

## Дерево для сравнения

Сказать «это сломала правка» можно, только если видно, что до правки было иначе. Проверяют это
вторым деревом, а не по памяти:

```bash
git worktree add ../<префикс>-base <коммит>   # ветка задачи не трогается
pnpm install --frozen-lockfile         # из ../<префикс>-base: node_modules у него свои
```

- Для сравнения берут не главную ветку, а последний коммит, на котором дерево собирается:
  главная бывает сломана, и тогда «до» и «после» различаются не из-за правки. Собирается ли
  коммит — проверяют сборкой, а не тем, что он в главной ветке.
- Стенд второго дерева поднимают на своих портах: порты сайта, админки и приёмника заняты владельцем, а порт отрисовки
  занимать нельзя — стенд разработчика ходит по имени `ssr:<порт отрисовки>`.
- Оба стенда держат поднятыми одновременно — ровно до конца сравнения: если сравнивать по памяти
  между двумя запусками, заметишь только то, что успел запомнить. Со сравнением стенд второго
  дерева гасится тем же ходом, а не оставляется до конца захода: оставленные стенды копятся
  заходами и держат соединения к хранилищу, и правило говорит об этом ловушкой. Снятие отбито —
  стенд называется владельцу в конце захода поимённо, с портом.

## Состояние портов снимается до первой сборки захода

Серверы владельца ложатся и без твоего участия: сайт отдавал 404 на все свои адреса ещё до
первой сборки захода, а API замолчало посреди него. Без замера «до» падение нельзя ни
приписать своей сборке, ни снять с неё подозрение.

```bash
for u in http://localhost:$API_PORT/health http://localhost:$SITE_PORT/ http://localhost:$ADMIN_PORT/; do
    printf '%s %s\n' "$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 "$u")" "$u"
done
```

Замер — это ответ, а не `lsof`: порт бывает занят собранным артефактом прошлой сессии, и он
отвечает 200 старым кодом.

## Частые промахи

- **Одиночная сборка проекта серверы переживают, и отказываться от неё незачем.** Замерено
  ответом до и после: все порты остались за своими процессами. Осторожность здесь стоит дороже
  проверки — целый набор проверок разметки остался незапущенным ровно потому, что сборку
  сочли опасной, не замерив. Сборка из кэша замером не бывает: она не собирает вовсе, и видно
  это по её длительности.
- Свой дев-сервер не поднимать: сайт, админка и приёмник уже подняты
  владельцем, и второй экземпляр отбивается гардом.
- **Отбитый статический сервер читается как запрет проверки, а он указание на верный ход.**
  Отдавать собранное им нельзя не из осторожности: приложение ходит на свой origin, а глубокая
  ссылка отвечает `404`. Отсюда идут не к обходу гарда, а к прокси дерева с его настоящим
  конфигом.
- **Дев-сервер владельца — место, где смотрят, а не место, где проверяют.** Вывод о том, что
  экран верен, делается на прод-сборке за настоящим прокси: разметка от сервера, локали, кэш,
  перенаправления и заголовки на дев-сервере либо другие, либо отсутствуют вовсе. Взгляд на
  поднятый дев-сервер годится, чтобы понять, что происходит на незнакомом экране, и не годится
  подтверждением: подтверждение — замер на стенде из прод-сборки.
- **Общая сборка глушит все три дев-сервера владельца, а не только API.** После
  `nx run-many -t build` ложатся и сайт, и админка. Собирать надо то, что
  проверяешь (`npx nx build site`), а не всё дерево. Если серверы легли, поднять их обратно
  агент не может — мешает гард, поэтому владельцу говорят об этом сразу, а не в конце сессии.
- Порт отрисовки занимать осторожно: стенд разработчика ходит по тому же имени `ssr:<порт отрисовки>`
  через `host-gateway`, и пока на нём висит чужой процесс, стенд отдаёт чужую сборку.
