# Спек домена

Паттерн правила `spec-driven`. Что при этом должно быть верно — закон
`docs/constitution/project-documentation.md`.

## Когда брать

- Заводится новый домен или фича, которой ещё нет.
- Правится контракт — спеки задетых доменов едут той же веткой.
- Замечено расхождение спека с кодом.

## Раскладка

```
<спеки>/<домен>/
    spec.md              — как домен работает
    implementation.md    — таблица «правило → файл:символ»
    scenarios.md         — сценарии SC-<ПРЕФИКС>-<НОМЕР>
    proposed/<фича>/     — только то, чего ещё нет
```

## Обязательные разделы

Набор разделов задан заранее и сверяется дословно: зачем, терминология, правила, что не входит,
контракт с кодами отказов, данные, экраны и состояния, сквозные требования, решения. «Не
применимо» — законный ответ, отсутствие раздела — нет: сквозные требования вспоминаются
постфактум именно тогда, когда для них не заведено места.

Шапка несёт статус, префикс сценариев, зависимости от других доменов, строку с законами,
которые домен применяет, и строку с корнями либ, чьи обработчики он обслуживает.

```markdown
**Зависимости:** `<домен>` (что берётся), `<домен>` (что берётся)
**Законы:** `access`, `locales`, `shared-code`
**Обработчики:** `<корень либы>`
```

Закон, названный где-нибудь в тексте спека, обязан стоять в этой строке: связь сверяется в обе
стороны.

## Правило и его привязка

Правило формулируется так, чтобы его можно было нарушить, и начинается с жирной фразы:

```markdown
- **Применяется одна максимальная скидка.** Сложение скидок даёт цену ниже себестоимости.
```

Привязка живёт в `implementation.md` рядом, ключ связи — сам текст правила:

```markdown
| Правило                               | Где исполняется   |
| ------------------------------------- | ----------------- |
| Применяется одна максимальная скидка. | `<путь>:<символ>` |
```

Правило, которому места в коде не нашлось, — намерение: ему место в открытых вопросах, а не
формальный якорь.

## Сценарий

```markdown
### SC-<ПРЕФИКС>-19 — подтверждение на занятые даты отбивается

Дано у записи есть подтверждённая соседняя на пересекающиеся даты
Когда владелец подтверждает заявку
Тогда отказ подаётся владельцу как занятые даты, а не как ошибка хранилища
```

Идентификатор ставится в начало заголовка теста, через тире. Сценарий без теста помечается
отметкой с причиной, сценарий с неполным тестом — отметкой о частичном покрытии.

## Порядок работы

1. Задача заводится сценариями: что станет верно, когда работа закончится.
2. Спек домена правится **до** кода.
3. Код пишется под сценарии, тесты называются их идентификаторами.
4. Проверка спеков — до пуша.
5. Приёмка идёт по сценариям, а не по пересказу правки.

## Частые промахи

- **Список шагов в спеке:** шаги — артефакт сессии, им место в ветке или в описании PR.
- **Скопированная из контракта таблица полей:** источник один, а компилируется из двух только
  одна.
- **Колонки и индексы в спеке:** они в схеме хранилища, а в спеке остаётся правило, которое
  ограничение выражает.
- **Место, где правило исполняется, внутри текста правила:** оно меняется при первом же
  переносе, и для него заведён отдельный файл.
- **Отметка о непокрытом при существующем тесте** — отказ: долг закрыли, а отметку не сняли.
- **Закон, названный в тексте, но забытый в шапке:** по закону тогда не узнать, какие домены на
  нём стоят.
- **Правка контракта без спеков задетых доменов** — гард документов отбивает такой коммит.
