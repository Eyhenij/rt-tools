# git-workflow-hosting — what is its own here

The bindings of this tree for the part `git-workflow-hosting` of the delivery rule, next to its `SKILL.md`.
The names of delivery and the rest of what is its own here are in the companion of
`git-workflow`.

## Where the articles are carried out

The first column is the article verbatim, as it is written in the section «How the law applies
here».

- **The PR of a task has the epic branch as its base — `gh pr create --base <ветка эпика>`.** — `.claude/hooks/git-guard-delivery-epic.sh:rt_epic_pull_base`. The base is read from the command. Not named at all, it means the default branch of the repository — the same case. A request already open is judged by `tools/board-epics.mjs:checkEpicPullBase`. A task outside an epic names no epic, the guard asks nothing, and its base is the main branch.
- **A PR in a chain has the previous branch as its base, not main.** — `.claude/hooks/git-guard-delivery-epic.sh:rt_epic_pull_base` — inside an epic the base is read from the command text and matched against the epic's branch: accepted are the epic branch itself and any branch standing on it, that is a neighbouring branch of the same chain; a missing `--base` counts as main, which is exactly the case the article is about. Outside an epic the base is checked by nothing — which of the two is right is known only by whoever branched, and for work unrelated to the previous one main is lawful.
- **The draft is not lifted from a branch that does not merge.** — `.claude/hooks/git-guard-delivery-draft.sh:conflicting` — mergeability arrives in the same answer as the reviewer and the review; with no field there is no requirement.
- **An index that branches only append lines to is declared a union of both sides.** — Not checked: the merge setting is read by no audit of the tree, and the host does not read it at all. The declaration lies in `.gitattributes` — the table of the records of the past and the table of the agreement domains.
- **The working tree is emptied before the PR opens, not after.** — Not carried out: the executor's working tree is seen by no check. The delivery guard judges the opening call, not what is left uncommitted next to it. Held by this article.
- **A push into a branch that has an open PR is followed by rereading its body.** — Not carried out: the body is read only at opening, by `.claude/hooks/git-guard-delivery-body.sh`, and after a push nothing rereads it. The queue audit judges the fact of a run on the tip, not what the body says about it. Held by this article.
- **On remarks to a PR the person is asked whether to answer under them, and after a yes each one gets an answer.** — **Not checked by anything.** An edit made for a remark looks like any other, and the question to the person leaves no trace on the host. Held by this article and by the section about remarks in the pattern `git-workflow-pr`.
- **The draft is not lifted while the PR has no review.** — `.claude/hooks/git-guard-delivery-draft.sh:rt_pull_state` — the PR state arrives from `tools/board.mjs`, and a requested reviewer or a review left by someone other than the author counts as a review.
- **What checks a PR whose base is not the main branch is asked before the first PR of an epic opens.** — `.github/workflows/ci.yml:branches` — the trigger here is narrowed to the main branch: a request into an epic branch gets no run at all, and the only check behind such work is the push gate.
- **A code edit is handed to a person by an open PR, not by a pushed branch.** — Not checked by anything: the delivery guard judges the opening of a PR but not its absence — work that ended with a push and never reached a PR it does not see at all. Held by this article and by the memory record about delivery.
- **What is not ready to merge opens as a draft — `gh pr create --draft`.** — Not checked by anything: the guard sees the call `gh pr create` and its keys, but does not know whether the plan's stages are closed. Held by the article and by the pattern `git-workflow-commit`.
- **A PR the pipeline does not wake for opens ready, without `--draft`.** — `.claude/hooks/git-guard-delivery-pipeline.sh:rt_delivery_pull_draft` — the guard reads the `pull_request` trigger of `.github/workflows/ci.yml`, named by `pushGate.pipelineFile` in `.claude/rt-kit/checks.json`. The trigger here is narrowed to `main`, so a PR into an epic branch with `--draft` is refused.
- **The PR body is written in the turn the PR opens, and next to the sample.** — `.claude/hooks/git-guard-delivery-body.sh:body_file` — at opening the guard reads the body file and demands its sections, the points table and the line linking to the task. When and next to what the body was written is checked by nothing. The queue audit finds only the consequence — a request without a line linking to the task.
- **The draft is lifted by a separate call — `gh pr ready <номер>`.** — The call itself is not demanded by a guard: the completeness of the work is invisible to a machine, and the sign here is the second message to the owner from the pattern `task-flow-close`. It is judged the other way round — `.claude/hooks/git-guard-delivery-draft.sh:pull_ref` refuses lifting the draft from a PR without a review.
- **The PR merge is pressed by a person, not by the work's executor.** — `.claude/hooks/git-guard-delivery-merge.sh:rt_delivery_merge_who` — on `gh pr merge` it refuses a merge into `main`, here by `RT_MAIN_MERGE_BY_OWNER=1`. It refuses a merge whose base the host did not name. With `RT_COMMIT_EMAIL` declared it takes one form only, the whole command: `RT_PULL_TOKEN_HINT`, then `gh pr merge <number> --merge --author-email <RT_COMMIT_EMAIL>`. Any other merge — a runner, a wrapper, a subshell, a chain, flags before the number — is refused by `rt_delivery_merge_said`; quotes and heredocs are text. The form here is `--merge`: squash and rebase are off on the host.
- **The identity of the call opening a PR is guarded by the delivery guard, not by the executor's memory.** — `.claude/hooks/git-guard-delivery-identity.sh:pull_token_var` — the substitution of `GH_TOKEN` is looked for in the text of the request-opening command, and a substitution answered by another account is refused; the request author is asked of `tools/board.mjs:pullState` on lifting the draft and matched against `RT_TASK_BOT`. Both strings are declared by the tree profile.
- **The PR author cannot be its reviewer.** — `tools/board.mjs:pullState` — the PR's author is struck out of its reviewers, and a review request on oneself does not count as a review. This is asked on lifting the draft. At opening `.claude/hooks/git-guard-delivery-identity.sh:pull_reviewer` refuses a reviewer equal to the account the token opens the PR by.
- **The host client call goes from the tree, and a command chain does not check the outcome.** — **Not checked by anything.** The directory the client was called from is invisible to the guards: they read the text of the command, not the working directory of the call. Held by reading the request body back in the same turn
- **PR labels, assignee and reviewer are set by `gh api` calls, not by `gh pr edit`:** — Not checked by anything: the guard judges the PR-opening call, not what its fields are edited by afterwards. Held by the article — on a repository with the old board `gh pr edit` never reaches the edit at all.
- **The machine commit's email is copied from the companion, not typed from memory.** — `.claude/rt-kit/project.sh:RT_COMMIT_EMAIL` — the same string as in the section about the signature below; `.claude/hooks/git-guard-delivery.sh` refuses a push if a commit of the branch's contribution named itself the machine account with a different address.
- **The identity of the machine account is confirmed by the host's answer:** — Not checked by anything: the guard matches a string against a string and does not ask the host at all — a network call would fall together with the connection. Held by the command from the section about the signature below, when the account is created and when its address changes.
- **Every commit of the branch's contribution is signed by the machine account, and the push set checks it.** — `.claude/rt-kit/project.sh:RT_HUMAN_EMAILS` — the mails of this tree's people; a commit of the contribution under an account outside the list and other than the machine one is refused on a push by the delivery guard helper `.claude/hooks/git-guard-delivery-signature.sh:rt_delivery_signature`. Carried out in part: the article names the push set, and here the refusal comes from the guard, so a push past the session is not judged.
- **The PR state is reread from the host right after publishing.** — **Not checked by anything.** The return code of a silently skipped request is the same as of one that was made; held by the request pattern
- **The host client's active account is chosen per machine, not per tree; the machine account is substituted per call, never made active.** — **Not checked by anything.** Signing into the client changes the state of the machine, while the guards judge the tree's calls. Held by the article; the active account is asked by `gh auth status`.
- **Reviewers are asked by a REST call, not by the client's selection.** — **Not checked by anything.** The client's selection is assembled by a GraphQL query and falls whole under the machine account token; the choice of way is held by this article

## What no machine judges here

- The green push set and the review before the merge — held by `task-delivery-loop`; a push without a green set is already refused by the push guard.
- Whether the owner gave the word on the epic of the base — it is written in the plan of that epic, and the guard does not read it.
- The call `gh api …/pulls/<N>/merge` — the guard does not read it; nor the owner's button in the browser, where there are no hooks at all.
