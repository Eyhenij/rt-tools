# Ветка, коммит и PR

Паттерн правила `git-workflow`. Что при этом должно быть верно — закон `docs/constitution/delivery.md`.

## Когда брать

- Заводится задача, с которой начинается правка.
- Заводится ветка под задачу.
- Готовится коммит или пуш.
- Открывается PR.
- Работа перешла на следующий шаг, и задача переставляется в другую колонку.

## Сначала план, потом задачи

Работа, из которой выходит больше одной задачи, начинается с плана, и план показывается
владельцу до того, как заведена первая задача. Разбивка — решение о том, что делается и в каком
порядке, и принимает его владелец, а не тот, кто заводит.

Заведённые до согласования задачи стоят в очереди как решённое дело: они показывают работу,
которую никто не заказывал, и убирать их потом дороже, чем не заводить.

Признак тот же, что у деления на ветки, — раздельный откат. Один дефект планом не описывается:
для него сразу заводится задача.

Плана нет, а работа делится — сначала пишется план, показывается, и только после ответа
владельца заводится первая задача. Ответ «делай» — тоже ответ; молчание им не является.

## Сначала задача, потом ветка

Заведение состоит из нескольких шагов: сама задача, номер в её заголовке, добавление в очередь,
начальное состояние. Очередь к репозиторию обычно не привязана, поэтому добавление само не
случается, и задача без него не видна ни в очереди, ни владельцу. Все шаги делает одна команда
— не рука.

Название задачи говорит, что не так, а не что сделать: PR потом переводит его в сделанное.
Номер в заголовок руками не пишется — он известен только после создания.

## Две задачи, которые чинятся одной правкой

Если по ходу выяснилось, что правка закрывает и соседнюю задачу, — это одна задача, а не две.
Слить их можно, пока правка не въехала в главную ветку: недостающее из поглощённой дописывается
в тело первой, и только потом поглощённая закрывается и снимается с очереди. Порядок важен —
удаление уносит с собой ссылки на неё из чужих тел.

После слияния ветки поглощения нет: она въехала, и откатывается целиком.

## Ветка заводится отдельным вызовом

Гард главной ветки разбирает текст команды и смотрит ветку на момент запуска, поэтому составная
команда отклоняется целиком — ветки в ней ещё нет:

```bash
✗ git checkout -b <ветка> && git commit -m '…'
✓ git checkout -b <ветка>
✓ git commit -F -
```

Имя ветки несёт номер задачи. Гард поставки разбирает его на месте и отбивает промах в форме до
первого коммита, а по номеру спрашивает очередь: задача должна существовать, быть открытой,
стоять в очереди и иметь исполнителя.

Имя без номера законно, пока ветка живёт локально — под пробу и разбор. PR с неё не откроется:
правка, доезжающая до главной ветки, начинается с задачи.

## Колонка задачи двигается вместе с работой

Ветка заведена — задача уже не в начальной колонке, а в работе. PR открыт — она ждёт разбора.
Оба перевода делает одна команда, вторым вызовом сразу за тем, который его вызвал.

Перевод не откладывается на потом: очередь читают между шагами, а не после них. Задача с
открытым PR, простоявшая в начальной колонке, всё это время выглядела нетронутой — и разбора за
неё никто не ждал.

## Коммит подписывается учётной записью машинной работы

Токен читается в переменную и не печатается; автор и коммиттер задаются переменными той же
команды. Правка общей настройки здесь не годится — она переписала бы подпись владельцу:

```bash
TOKEN=$(tr -d '\n' < <файл с токеном>)

GIT_AUTHOR_NAME="<бот>" GIT_AUTHOR_EMAIL="<адрес бота>" \
GIT_COMMITTER_NAME="<бот>" GIT_COMMITTER_EMAIL="<адрес бота>" \
    git commit -F -
```

Заголовок — `тип(область): описание`, без точки в конце. Набор типов и областей задан
настройкой проверки заголовка.

## Документ едет тем же коммитом

Гард документов требует пару и называет её сам. Обход — строка в теле коммита, причина
обязательна:

```
Docs-skip: правка только в сценариях хука, зеркала у него нет
```

## Номер задачи стоит в её заголовке и в заголовке PR

Форма одна на оба. Номер стоит в самом заголовке, а не только в теле: в списке PR тела не
видно. Тот же номер несёт и имя ветки — поэтому задача, ветка и PR читаются как одно.

Задача говорит, что не так; PR тем же номером отчитывается, что сделано. Инфинитив из задачи в
заголовок PR не переносится: «исправить» становится «исправлено».

Тип и область коммита в заголовок PR не идут: род правки и область уже видны метками.

## PR прикрепляется к задаче

Тело начинается со строки связи с задачей — по ней в очереди заполняется поле связанных PR.
Ревьювер, исполнитель и метки задаются той же командой, и PR без них не открывается.

Ревьювер — всегда владелец: без запроса разбора PR не показывается ему в очереди. Метки берутся
у задачи целиком — и род правки, и все её области; читаются они у задачи, а не выбираются по
памяти.

Строка связи обязательна: без неё PR не прикрепляется к задаче. Она же означает, что задача
закрывается целиком — половину задачи одним PR не выкатывают: у задачи одна ветка, и работа,
которая в неё не влезает, делится на задачи до того, как ветка заводится.

Тело перечитывается всякий раз, когда в ветку что-то влилось после публикации: отчёт утверждает
про дерево, а дерево с тех пор изменилось.

## Что проверяется до публикации PR

Проверок на самом PR нет: выкатка запускается пушем в главную ветку, и до слияния никто не
гоняет ничего. Линтеры и юниты снимает гейт пуша — ниже то, чего он не знает.

1. **В ветке только та правка, за которой её заводили** — сводка расхождения с главной веткой.
   Чужой домен в списке файлов означает, что правка расползлась.
2. **Ни мока, ни подменённого ответа, ни отладочной строки** — расхождение читается целиком, а
   не по именам файлов. На прод они уезжают молча и портят настоящие данные.
3. **Документ едет тем же коммитом.** Пару называет гард, но спек домена и правку его поведения
   он не знает — это остаётся за автором.
4. **Проверки текстов и раскладки зелёные.**
5. **Все приложения собираются.** Гейт пуша сборку обычно не гоняет.
6. **Видимый текст заведён во всех локалях.**
7. **Правка вёрстки подтверждена замером**, а не взглядом, и снята при узком экране — паттерн
   `browser-verification-measure`.
8. **Правка публичной разметки проверена на прод-сборке по всем локалям** — паттерн
   `seo-verify`.
9. **Тело PR начинается строкой связи с задачей**, а метки, ревьювер и исполнитель стоят.
10. **Заголовок PR несёт номер задачи и называет её сделанной** — тем же номером, что у задачи
    и в имени ветки.
11. **Очередь работ сходится.** Задача в очереди, с исполнителем и номером в заголовке; PR один
    на задачу, и закрывает он её целиком.

Сразу после публикации задача переставляется в разбор, и сверка очереди прогоняется ещё раз: до
открытия PR колонку она не судит, а после открытия расхождение видит.

Сделанное рассуждением и сделанное замером в теле PR разводятся прямо: непроверенное, названное
проверенным, ревьювер принимает за проверенное.

## Частые промахи

- **Добавление в индекс нескольких путей не добавляет ничего, если хоть один путь не
  существует.** Команда обрывается на первом промахе целиком, а следующая правка последнего
  коммита уносит в него всё, что осталось в индексе. Состав коммита читается сразу после него,
  а не на разборе PR.
- **Задача, заведённая мимо команды, в очередь не попадает и гардом не отбивается** — он
  смотрит команду, а не задачу. Ловится это только сверкой очереди.
- **Исполнитель у задачи сам не проставляется** ни при заведении через веб, ни при добавлении в
  очередь.
- **Колонка сама не двигается** ни от заведения ветки, ни от открытия PR: очередь ветки не
  видит вовсе, а связь с PR заполняет только поле связанных PR.
- **Постраничный обход очереди через общий флаг уходит в повтор первой страницы** — курсор
  берётся из ответа руками, а полнота сверяется с общим числом элементов.
