# Спека на чистую функцию и на обработчик

Паттерн правила `testing`. Что при этом должно быть верно — закон
`docs/constitution/verifiability.md`.

## Когда брать

- Заводится или правится файл спеки рядом с исходником.
- Логику надо вынести из компонента или службы, чтобы её стало чем проверить.
- Пишется спека на обработчик серверной стороны.

## Импорты явные

Даже когда прогонщик кладёт свои имена в глобальную область, список пишется: файл, читаемый
без конфига, не должен зависеть от настройки, о которой в нём ни слова.

## Один блок на функцию

Имя блока совпадает с именем функции дословно; заголовки тестов — предложения настоящим
временем, о поведении, а не об устройстве:

```
описание('applyDayClick', () => {
    тест('SC-<ПРЕФИКС>-19 — нажатие по занятому дню ничего не меняет', () => {
        ожидать(applyDayClick(day('2026-08-12'), selection)).равно(selection);
    });
});
```

Идентификатор сценария из спека домена стоит в начале заголовка, через тире. Краевые случаи —
отдельные тесты в том же блоке, а не один тест с десятком проверок.

## Фикстура собирается функцией с частичной подменой

Не повторяющимся литералом: литерал, размноженный по файлу, при первой же новой обязательной
колонке правится в каждом месте — и в одном обязательно забывается.

```
функция day(iso, подмена = {}) {
    вернуть { iso, dayOfMonth: число(iso.срез(8)), busyNight: занято(iso), past: ложь, ...подмена };
}
```

Общие константы лежат наверху файла, в области модуля.

## Решение выносится в чистую функцию

Логика уезжает в отдельный файл рядом и проверяется вызовом — без подъёма каркаса и без
подмены зависимостей. Компонент и служба остаются обёрткой, у которой своего ветвления нет.

## Обработчик зовётся напрямую

Обработчик — метод класса; двойник хранилища пишется руками. Проверяются порядок действий,
откат при отказе половины, идемпотентность повтора и то, что именно ушло в хранилище. Раскладку
полей стерегут тесты слоя обращения к серверу, и здесь она не повторяется.

## Разовый тест-доказательство

Дефект, который иначе подтверждается только чтением кода, доказывается тестом, написанным на
время разбора: он поднимает настоящий обработчик, подменяет его единственный выход наружу и
считает походы.

Число до правки и число после — единственная форма ответа, которую такая проверка даёт: «сто из
ста» и «двадцать из ста» различимы, а «код выглядит правильным» — нет.

Второй способ снять «до» — вернуть на место версию файла из точки расхождения ветки и прогнать
тест ветки: падение теста и есть воспроизведение дефекта. Файл после этого восстанавливается
копией, и восстановление проверяется прогоном того же теста, а не памятью.

Двойники соседей не выдумываются: рабочий набор берётся из теста соседнего обработчика того же
домена. Двойник, собранный по типу, падает не на утверждении, а на вызове метода, которого у
него нет.

**Такой файл не коммитится.** Он живёт до конца разбора и удаляется вместе с ним; проверка,
которую стоит оставить, переписывается в обычную спеку с идентификатором сценария в заголовке.
Признак временного файла — его заголовок не называет ни одного сценария.

## Частые промахи

- **Либа без своего конфига прогонщика проходит зелёной, не запустив ни одного файла.** Прежде
  чем писать первый тест в либе, проверить, что конфиг рядом есть.
- **Подмена модуля скрыла бы то, ради чего тест и заводится** — какой именно вызов ушёл в
  хранилище и в каком порядке. Двойник пишется руками.
- **Своих помощников для проверок не заводить** — утверждения пишутся прямо.
- **Заголовок с несуществующим идентификатором сценария роняет проверку спеков**, а сами тесты
  при этом остаются зелёными.
