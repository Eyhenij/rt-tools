# code-design — how it is arranged here

The names of this tree next to the rule `SKILL.md` beside it.

## Where it lives

- **the layer that brings the rule** — `.claude/hooks/skill-gate-layers.sh`, called by `.claude/hooks/skill-gate.sh`; the demonstration components of the showcase and the linter settings are lifted by `skill_layer_skip` in `.claude/rt-kit/gate-map.sh`
- **the check of coupling** — `tools/check-coupling.mjs`: `--module=<path>` gives the numbers for the plan, `--base=origin/<base>` gives «was → became» of the branch; the roots, the declared blocks and the harness are in `coupling` of `.claude/rt-kit/checks.json`
- **the old cycles and imports past an entry** — `tools/coupling-allowlist.json`, each with its reason and task; a new one is lifted only by a reason that begins with the owner's words
- **the borders of libraries** — `@nx/enforce-module-boundaries` in `eslint.config.mjs` with `eslint/boundaries/domains/`
- **the second copy** — `tools/check-dupes.mjs`; **the unused export** — `knip.json`
- **the size of a module** — `max-lines` in `eslint.config.mjs` and `tools/check-file-size.mjs`
- **the plan and the progress** — `docs/tasks/<branch>/`

## Where the articles are carried out

- **The executor chooses modules, bounds, terms and patterns before the code and writes them in the plan.** — `.claude/hooks/skill-gate-layers.sh:code-design-choose` — a grill and a plan are refused until the rule and the table are loaded. A plan without the section, without a row of the table, or with a row of fewer than two words is not written: `tools/flow-decision.mjs:decisionProblems`, called on a write of `docs/tasks/<branch>/plan.md` by `.claude/hooks/flow-step-guard.sh`. The one line «Решения нет: <reason>» stands for the whole table. An approved plan, a template being filled in and the plan mode of the host are not judged.
- **A chosen pattern is written with its place, its problem and the simpler way dropped.** — `tools/flow-decision.mjs:decisionProblems` — a pattern without its place «`<path>:<symbol>`» is not written, unless the row says «паттерна нет: <reason>»; at the end of the stages `tools/task-flow/measure/design.mjs:held` asks that the place is declared in the code. The problem and the simpler way dropped are read by the roles.
- **Code is read first: who imports the module and whom it imports.** — **Not checked by anything.** The code graph answers relations; reading leaves no trace.
- **Coupling is counted before and after the edit.** — `tools/check-coupling.mjs:growthLeft` — the push set refuses outgoing links grown past the first plan of the branch; scenario SC-AK-1960. Incoming links are printed. The row of the coupling in the plan names a number «`<path>` исходящие N → M» or «кода нет: <reason>»: `tools/flow-decision.mjs:decisionProblems`. A link through a template, a name in a variable and a script started from code are not counted.
- **A module has one duty, said in one sentence without «and».** — **Not checked by anything.** A reader of the plan and of the diff judges it.
- **Isolation: from outside a module is called through its entry and tested without its neighbours.** — `tools/check-coupling.mjs:structureLeft` — a new import past an entry is refused; between packages and libraries `eslint.config.mjs:enforce-module-boundaries` holds it too. The folders of the package scripts have no entry, and for the test without neighbours nothing holds it.
- **An import goes from the detail to the decision.** — `eslint.config.mjs:enforce-module-boundaries` — the direction between libraries; inside a package only a reverse link is seen, as a cycle of blocks by `tools/check-coupling.mjs`, and for a decision without disk and network nothing holds it.
- **Only what a neighbour calls is exported.** — `knip.json:entry` — `pnpm run check:unused`, where the file is not an entry itself: the exports of `tools/`, of the package assets and of the kit components are judged by nothing, and the functions of scripts neither.
- **A decision lives in one module.** — **Not checked by anything.** `tools/check-dupes.mjs` sees repeated exports and settings, not a repeated condition.
- **A cycle between modules is broken by moving the shared part out.** — `tools/check-coupling.mjs:structureLeft` — a new cycle of modules or of blocks is refused, scripts included; scenario SC-AK-1958. The old ones lie in the list with their task.
- **Each input form is named with its source and an example and has a test case, a refused one too.** — `tools/flow-decision.mjs:decisionProblems` — a row of input without a scenario number or without a suite is not written, unless it says «номера нет: <reason>» or «ввода нет: <reason>». At the end of the stages `tools/task-flow/measure/design.mjs:held` asks that the suite stands, carries the number and was touched or carried it at the plan commit. The source, the example, the refused case and whether every form is named are read by the roles.
- **Bounds are written: contracts, versions and safety that stay, imports that are forbidden.** — `tools/flow-decision.mjs:decisionProblems` — a table without the row, or with a row of fewer than two words, is not written. Whether the bounds hold is judged by a reader of the plan.
- **The priority is named: which of speed, memory, simplicity and reliability wins.** — `tools/flow-decision.mjs:decisionProblems` — the same for the row of the priority; the choice itself is judged by a reader of the plan.
- **The budget is a number before the code: files, lines, dependencies.** — `tools/flow-decision.mjs:decisionProblems` — the row names a path with «до N» or «плюс N», the new code files and the new dependencies by number. At the end of the stages `tools/task-flow/measure/design.mjs:held` compares them with the head: «до N» with the lines of the file, «плюс N» with its growth. A number passed without a line of the decisions is refused.
- **The diff holds only what the steps need.** — `tools/task-flow/measure/design.mjs:held` — at the end of the stages a new file of code named neither by the modules nor by the footprint is refused. In the same exit `tools/task-flow/measure/footprint.mjs:touched` asks that every path of a footprint row marked «(правится)» was touched. A line beside the plan in an old file is seen by a reader.
